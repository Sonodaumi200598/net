# 第 2 章 异构聚合网络架构

本章面向无人机、无人车实时图像回传场景，说明聚合路由器到聚合服务器之间的系统组成、关键功能定位和异构链路类型。该架构的核心目标是将多种通信链路统一纳入可管理、可调度、可监测的传输体系，为后续链路质量感知、多路径调度、乱序重排、丢包恢复和视频质量保障提供基础。

本章关注范围如下：

```text
无人机 / 无人车视频流
        ↓
聚合路由器
        ↓
4G/5G、Wi-Fi、有线、卫星、专网、仿真链路
        ↓
聚合服务器
```

其中，无人机和无人车侧的视频采集与编码模块作为上游输入，不在本章展开；聚合服务器之后的业务平台、播放平台、存储系统和 AI 识别系统也不作为本章重点。

## 2.1 系统组成

异构聚合网络主要由聚合路由器、异构通信链路、聚合服务器以及配套的链路管理、隧道、容器化和监控组件组成。

### 2.1.1 聚合路由器

聚合路由器部署在无人机、无人车或其近端通信节点上，是视频流回传过程中的发送侧核心设备。它负责接收上游实时视频流，并将视频数据按照一定策略分发到多条异构链路。

常见设备形态包括：

- Linux 工控机：适合实验验证、车载平台和边缘计算场景，扩展能力强，便于部署自定义传输程序。
- OpenWrt 路由器：适合轻量级网络聚合、移动路由和嵌入式场景，便于管理多网卡和网络接口。
- 边缘计算盒子：通常具备更强 CPU/GPU/NPU 能力，可同时承担视频预处理、链路管理和传输调度任务。

对于无人车场景，聚合路由器一般可安装在车体内部，通过 5G 模组、Wi-Fi 网卡、以太网口或专网电台接入外部网络。对于无人机场景，聚合路由器可能部署在机载端，也可能部署在地面控制站或中继节点上。

### 2.1.2 聚合服务器

聚合服务器是异构聚合网络的接收侧核心节点，负责接收来自多条链路的数据包，完成数据包解析、去重、排序、缓存、统计和重组，并将恢复后的视频流输出给后续系统。

常见部署形态包括：

- Linux 云服务器：适合公网可达的远程回传场景，便于无人机、无人车通过运营商网络主动连接。
- 边缘服务器：适合园区、港口、矿区、应急现场等低时延场景，可部署在距离任务区域较近的位置。
- 中心机房服务器：适合统一接入、集中存储和指挥调度场景，通常具备更完善的网络、安全和运维条件。

聚合服务器通常需要具备稳定公网地址或可被聚合路由器访问的固定入口，同时需要支持多端口、多会话和多视频流并发接入。

### 2.1.3 网络接口

网络接口是聚合路由器接入异构链路的基础。不同接口对应不同的物理链路或逻辑通道。

常见接口包括：

- 多 5G 模组：用于接入不同运营商或不同频段的蜂窝网络，提高移动场景下的覆盖和可靠性。
- 多 Wi-Fi 网卡：用于接入现场 Wi-Fi、Mesh Wi-Fi 或热点网络，适合短距离高带宽回传。
- 以太网口：用于有线接入、固定站点、实验基准链路或服务器侧接入。
- 卫星终端：用于公网和地面专网不可用时的远距离兜底通信。
- 专网通信接口：用于 COFDM、LTE 专网、5G 专网、Mesh 电台等行业通信链路。

在操作系统中，这些接口通常表现为 `eth0`、`wlan0`、`wwan0`、`usb0`、`tun0`、`wg0` 等网络设备。聚合路由器需要能够识别每个接口对应的链路类型、IP 地址、网关、在线状态和质量指标。

### 2.1.4 隧道技术

实际部署中，聚合路由器到聚合服务器之间不一定直接裸传业务数据，常常会在不同物理链路之上建立逻辑隧道。隧道可以统一地址空间、简化链路管理、增强安全性，并帮助服务器区分不同链路来源。

常见隧道技术包括：

- VPN：泛指虚拟专用网络，可用于构建安全传输通道。
- WireGuard：配置简单、性能较好，适合移动节点和边缘节点之间建立加密隧道。
- GRE：轻量级三层隧道，适合封装 IP 流量，但本身不提供加密。
- VXLAN：常用于二层网络扩展和数据中心场景，在实验中可用于构造逻辑网络。
- IPSec：成熟的网络层安全协议，适合对安全性要求较高的行业场景。

使用隧道时需要特别关注 MTU。由于隧道会增加额外包头，如果不控制业务包大小，容易导致 IP 分片，进而放大丢包影响。

### 2.1.5 容器化部署

实验阶段可以使用 Docker 和 Docker Compose 将视频源、聚合路由器、链路仿真节点、聚合服务器和监控模块拆分为多个容器。这样可以提高实验环境的可重复性和可迁移性。

容器化部署适合完成以下工作：

- 快速搭建单机多节点实验拓扑。
- 为不同链路设置独立网络命名空间。
- 结合 `tc netem` 模拟时延、抖动、丢包、乱序和限速。
- 独立部署聚合路由器程序、聚合服务器程序和监控组件。
- 便于后续进行自动化测试和性能对比。

## 2.2 聚合路由器功能定位

聚合路由器是异构聚合传输过程中的发送侧控制点。它不仅承担普通路由器的数据转发功能，还需要具备视频流接入、链路状态感知、包级调度、链路选择、队列管理和传输状态统计能力。

### 2.2.1 多网卡绑定与管理

聚合路由器需要同时管理多种网络接口，并保证每条链路可独立配置、独立检测和独立调度。

相关实现技术包括：

- Linux NetworkManager：用于管理蜂窝、Wi-Fi、有线等网络连接。
- `iproute2`：用于查看和配置 IP 地址、路由表、策略路由和网络接口状态。
- 多网卡管理：用于维护每个接口的在线状态、IP 地址、网关、DNS 和链路优先级。
- 接口状态检测：用于发现网卡掉线、重新拨号、信号下降或链路恢复。

在无人机、无人车移动环境下，多网卡管理不仅要判断接口是否存在，还要判断该接口对应的链路是否真正可达聚合服务器。

### 2.2.2 策略路由

策略路由用于保证不同链路的数据包从指定接口发出。没有策略路由时，多网卡设备可能因为默认路由冲突导致所有数据都走同一出口，无法形成真正的多路径传输。

相关实现技术包括：

- `ip rule`：根据源地址、fwmark、目标地址等条件选择路由表。
- `ip route table`：为每条链路维护独立路由表。
- 源地址绑定：发送程序绑定指定链路的源 IP，保证返回路径和链路标识清晰。
- fwmark 标记：通过防火墙或程序标记数据包，再由策略路由选择出口链路。

典型逻辑如下：

```text
链路 A 数据包 -> 绑定源 IP A -> 查询路由表 A -> 从接口 A 发出
链路 B 数据包 -> 绑定源 IP B -> 查询路由表 B -> 从接口 B 发出
链路 C 数据包 -> 绑定源 IP C -> 查询路由表 C -> 从接口 C 发出
```

策略路由是 MPUDP、自定义 UDP 聚合协议、多链路隧道等方案能够正常工作的基础。

### 2.2.3 包调度程序

包调度程序决定每个视频数据包走哪条链路，是聚合路由器的核心逻辑之一。

可选实现方式包括：

- 用户态 UDP 转发程序：实现简单，便于实验验证和算法迭代，适合作为初期实验模型。
- eBPF：可在内核路径中执行部分包处理逻辑，适合后续优化包分类、统计和高性能转发。
- DPDK：绕过内核网络栈进行高速包处理，适合高吞吐、低时延场景，但开发复杂度较高。

实验初期建议优先采用用户态 UDP 转发程序。其优势是实现清晰、调试方便，可以快速验证轮询调度、加权调度、链路质量感知调度和视频帧重要性感知调度。

### 2.2.4 视频流接入

聚合路由器需要接收来自无人机、无人车的视频编码流。上游视频流可能来自机载编码器、车载编码器、摄像头推流模块或边缘处理模块。

相关实现技术包括：

- FFmpeg：用于拉流、推流、转封装、录制和测试视频输入输出。
- GStreamer：用于构建灵活的视频处理 pipeline，适合嵌入式和实时处理场景。
- RTP 输入：适合实时音视频传输，具备序号、时间戳和载荷类型等信息。
- MPEG-TS/UDP 输入：适合工程测试和流媒体传输，易于与 FFmpeg 对接。

聚合路由器在本实验模型中不重点承担复杂的视频解码和画面分析任务，而是以视频流接入、传输封装和链路调度为主。

### 2.2.5 链路状态采集

聚合路由器需要持续采集每条链路的基础质量指标，为后续调度决策提供依据。

相关实现技术包括：

- ICMP：通过 ping 测量基础连通性和 RTT。
- UDP probe：通过自定义探测包测量链路往返时延、丢包和可达性。
- RTCP feedback：在 RTP 体系中获取接收端反馈，包括丢包、抖动和接收质量。
- 自定义 ACK：由聚合服务器返回数据包接收确认，用于估计 RTT、丢包率和吞吐能力。

链路状态采集不仅要判断“能不能连通”，还要判断“当前适不适合承载实时视频数据”。因此应同时关注时延、抖动、丢包、带宽和队列积压趋势。

## 2.3 聚合服务器功能定位

聚合服务器是异构聚合传输过程中的接收侧控制点。它负责接收来自多条链路的数据包，并将多路径到达的数据恢复为连续、可用的视频流。

### 2.3.1 多端口监听

聚合服务器可以通过多种方式接收聚合路由器发来的数据。

相关实现技术包括：

- UDP socket：适合自定义 MPUDP 数据通道，低时延、实现灵活。
- QUIC endpoint：适合需要加密、连接迁移和拥塞控制的传输方案。
- SRT listener：适合作为可靠视频传输对比方案或单链路回传方案。
- 多端口监听：不同链路或不同视频流使用不同端口，便于调试和统计。
- 单端口接收：通过包头中的 `path_id`、`flow_id` 区分链路和视频流，便于统一管理。

实验中可以采用“多端口接收 + 自定义包头”的方式降低调试难度，也可以在后续优化为单端口多链路统一接收。

### 2.3.2 高并发接收

当无人机、无人车数量增加，或者单个平台回传多路摄像头画面时，聚合服务器需要具备较强的并发接收能力。

相关实现技术包括：

- epoll：Linux 下常用高并发 I/O 机制，适合大量 socket 事件监听。
- io_uring：较新的 Linux 异步 I/O 机制，适合高性能网络收发。
- async runtime：如 Tokio、asyncio、libuv 等，用于构建异步接收与处理流程。
- 多线程接收：将链路接收、数据解析、重排重组和输出处理拆分到不同线程。

对于实验模型，epoll 或异步 runtime 已能满足多数验证需求。io_uring 和 DPDK 可作为后续性能优化方向。

### 2.3.3 数据重组

多链路传输会造成数据包乱序、重复和迟到。聚合服务器需要根据包头中的流标识、序号和时间戳对数据进行缓存和重组。

相关实现技术包括：

- ring buffer：适合固定窗口内的包缓存和连续序号处理。
- priority queue：适合按照全局序号或播放时间戳取出最早应输出的数据包。
- hash map：适合根据 `flow_id`、`seq`、`fec_group_id` 快速定位包状态。
- jitter buffer：用于吸收网络抖动，降低乱序对视频输出的影响。

重组模块需要在完整性和实时性之间做权衡。如果等待时间过长，视频时延会升高；如果等待时间过短，缺失包可能造成画面损伤。

### 2.3.4 去重与排序

在冗余发送、重传和多路径传输中，服务器可能收到重复数据包。服务器需要对数据包进行去重，并按照原始顺序输出。

相关实现技术包括：

- sequence number：为每个数据包设置全局序号，作为排序和丢包检测依据。
- sliding window：维护接收窗口，判断数据包是否在可接受范围内。
- duplicate discard：对重复序号的数据包进行丢弃。
- gap detection：发现序号缺口，触发等待、FEC 恢复或 NACK 重传请求。

服务器侧通常需要为每一路视频维护独立接收窗口，避免不同视频流之间相互影响。

### 2.3.5 输出接口

聚合服务器完成接收和重组后，需要将恢复后的视频流输出给后续系统。

常见输出方式包括：

- UDP/RTP 输出：适合低时延播放、转发和后续实时处理。
- RTMP 推流：适合接入传统直播平台或流媒体服务器。
- WebRTC 转发：适合浏览器端低时延观看和交互式应用。
- 文件存储：适合实验记录、质量分析和事后回放。

实验阶段可以优先使用 UDP/RTP 输出或文件存储，便于通过 FFmpeg、VLC、Wireshark 等工具验证重组结果。

## 2.4 异构链路类型

异构链路是聚合路由器和聚合服务器之间的实际传输基础。不同链路的能力差异决定了调度策略、冗余策略和故障恢复策略的设计方向。

| 链路类型 | 实现方式 | 典型特点 | 适用角色 |
|---|---|---|---|
| 5G/4G | USB 5G 模组、CPE、蜂窝路由器 | 覆盖范围广，移动性好，带宽和时延随网络状态波动 | 主力链路、辅助链路、备用链路 |
| Wi-Fi | Wi-Fi STA、Wi-Fi Mesh、热点接入 | 局部区域带宽较高，部署方便，但易受干扰和遮挡影响 | 近距离高带宽链路、园区链路 |
| 有线 | 千兆以太网 | 高带宽、低时延、低丢包，稳定性强 | 实验基准链路、固定站点链路 |
| 卫星 | 卫星通信终端 | 覆盖范围广，不依赖地面网络，但时延较高、成本较高 | 远距离兜底链路、应急链路 |
| 专网 | COFDM、LTE 专网、Mesh 电台 | 可控性和安全性较强，适合行业任务区域 | 可靠业务链路、任务专用链路 |
| 仿真链路 | Linux network namespace + `tc netem` | 可重复模拟带宽、时延、抖动、丢包、乱序和中断 | 实验验证链路、算法评估链路 |

### 2.4.1 5G/4G 链路

5G/4G 链路是无人机、无人车视频回传中最常见的公网链路。聚合路由器可通过 USB 5G 模组、5G CPE、蜂窝路由器或多 SIM 模组接入运营商网络。

该类链路适合作为主力视频回传链路，但其带宽、RTT 和丢包率受信号强度、基站负载、移动速度和运营商核心网路径影响较大。多运营商蜂窝链路可以进一步提高移动场景下的覆盖可靠性。

### 2.4.2 Wi-Fi 链路

Wi-Fi 链路适合园区、仓库、港口、矿区、校园等局部区域内的高带宽回传。无人车在固定区域运行时，可以通过 Wi-Fi STA、Wi-Fi Mesh 或热点接入方式回传视频。

Wi-Fi 的主要问题是覆盖范围有限、干扰明显、漫游切换不稳定。因此在聚合架构中，Wi-Fi 通常适合作为近距离高带宽辅助链路，而不是大范围移动场景的唯一链路。

### 2.4.3 有线链路

有线以太网链路具备高带宽、低时延、低丢包和高稳定性，常用于实验环境、地面固定节点、服务器接入和设备调试。

在实验模型中，有线链路非常适合作为基准链路，用于和 5G、Wi-Fi、专网、卫星等链路进行对比。通过设置有线链路为低时延、低丢包路径，可以观察多路径调度在理想链路和波动链路之间的选择行为。

### 2.4.4 卫星链路

卫星链路适合山区、海域、灾区、荒漠等缺少地面网络覆盖的场景。其优势是覆盖范围广，不依赖运营商基站和现场网络基础设施。

但卫星链路通常存在较高时延、较大抖动、较高成本和终端功耗限制。在实时视频回传中，卫星链路更适合作为低码率兜底链路、应急链路或关键数据备份链路。

### 2.4.5 专网链路

专网链路包括 COFDM 图传、LTE 专网、5G 专网、Mesh 电台和微波链路等。此类链路通常服务于特定行业场景，如应急救援、矿区巡检、港口作业、电力巡检和安防巡逻。

专网链路的优势是可控性强、安全性较好、任务区域内稳定性较高。其不足是建设和维护成本较高，覆盖范围依赖现场部署，链路带宽也可能低于公网 5G。

### 2.4.6 仿真链路

仿真链路用于实验阶段构造可控网络环境。通过 Linux network namespace、veth、bridge 和 `tc netem`，可以在单机或容器环境中模拟多条不同质量的链路。

可模拟的链路特性包括：

- 带宽限制。
- 固定时延。
- 时延抖动。
- 随机丢包。
- 突发丢包。
- 数据包乱序。
- 数据包重复。
- 链路中断与恢复。

仿真链路的价值在于可重复、可对比、成本低，适合在真实设备测试前验证聚合协议、调度算法和服务器重组机制。

## 2.5 本章小结

异构聚合网络架构的核心是将多种链路统一接入聚合路由器，并由聚合路由器根据链路状态和视频业务需求选择合适路径发送数据。聚合服务器则负责从多条链路接收数据，完成去重、排序、缓存、重组和输出。

从实现角度看，本章涉及的关键技术包括：

- 聚合路由器设备形态：Linux 工控机、OpenWrt 路由器、边缘计算盒子。
- 聚合服务器部署形态：Linux 云服务器、边缘服务器、中心机房服务器。
- 网络接口：多 5G 模组、多 Wi-Fi 网卡、以太网口、卫星终端、专网接口。
- 隧道技术：VPN、WireGuard、GRE、VXLAN、IPSec。
- 路由与网卡管理：NetworkManager、`iproute2`、`ip rule`、`ip route table`。
- 数据收发与调度：UDP socket、QUIC endpoint、SRT listener、用户态 UDP 转发、eBPF、DPDK。
- 数据结构与重组：ring buffer、priority queue、hash map、sequence number、sliding window。
- 实验部署：Docker、Docker Compose、Linux network namespace、`tc netem`。

该架构为后续传输协议选择、多路径调度、链路质量感知、乱序重排、丢包恢复和视频质量评价奠定基础。
