# 第 9 章 实验环境基础技术

## 9.1 单机网络仿真

单机实验可使用 Linux network namespace、veth pair、bridge 和 tc netem 构造聚合路由器、多条虚拟链路和聚合服务器。

该方式成本低、可重复性强，适合基础功能验证和算法对比。

为了真实形成多路径，聚合路由器必须具有多个独立虚拟接口，每条接口连接不同的链路 namespace，并配置独立源地址、策略路由表和 `path_id`。如果所有接口最终仍查询同一个默认路由或进入同一个未区分的 bridge，实验看到的只是多网卡形式，而不是真正可独立控制的多条路径。

## 9.2 容器化实验环境

容器化实验可使用 Docker 和 Docker Compose 搭建多个逻辑节点。每个容器可模拟视频源、聚合路由器、链路节点、聚合服务器或监控组件。

容器网络可结合 tc 工具模拟带宽限制、时延、抖动、丢包和链路中断。

Docker 默认网络可能引入额外 NAT 和 bridge，导致源地址、路径 MTU 和路由行为与设计不一致。建议让聚合路由器、链路节点和聚合服务器分别使用独立 network namespace，或为容器显式配置多网络、固定地址和策略路由。管理 SSH、日志和镜像下载应走独立管理网络，避免影响 MPUDP 实验数据。

## 9.3 网络损伤模拟

基础实验需要模拟以下网络损伤：

- delay：固定时延。
- jitter：时延抖动。
- loss：随机丢包或突发丢包。
- duplicate：重复包。
- reorder：乱序包。
- corrupt：随机比特差错。
- bandwidth limit：带宽限制。
- link down/up：链路中断与恢复。

`tc netem` 适合注入时延、抖动、丢包、重复、乱序和随机损坏；准确的带宽与队列限制应结合 TBF、HTB 或 CAKE/FQ 等 qdisc，而不是仅设置 `netem rate`。乱序测试必须同时配置足够的延迟差，否则数据包可能仍按原顺序离开队列。

`tc netem corrupt` 注入的数据有可能先被 IP/UDP 校验和发现并由内核丢弃，因此不能单独证明应用层 CRC32C 已正确工作。验证 CRC32C 和 AES-GCM 时，应在加密完成后、服务器校验前使用隔离的中间测试程序修改密文、包头或认证标签，并在需要时重新计算外层 UDP 校验和，使测试包能够到达应用层；随后分别验证 CRC 差错包和恶意篡改包是否被拒绝。

| 工具 | 作用 |
|---|---|
| FFmpeg | 视频推流、拉流、录制、转码和码流分析。 |
| GStreamer | 构建实时视频处理 pipeline。 |
| iperf3 | 测试单链路或多链路吞吐量。 |

## 9.5 推荐实验拓扑

```text
视频源 / FFmpeg
       │ RTP/PS/H.265
       ▼
聚合路由器 namespace
       │
       ├── veth_fiber ── 光纤链路 namespace ──┐
       ├── veth_5g    ── 5G 链路 namespace   ──┼── 聚合服务器 namespace
       └── veth_wifi  ── Wi-Fi 链路 namespace ─┘
                         │
                         ├── MPUDP 视频数据接收
                         ├── QUIC ACK/NACK 与链路反馈
                         └── PostgreSQL/TimescaleDB 指标存储
```

每个链路 namespace 分别配置带宽、基础时延、抖动、队列长度、丢包和乱序参数。聚合路由器按源地址或 fwmark 查询独立路由表，发送程序绑定指定接口，服务器根据 `session_id + path_id` 分别统计三条路径。这样才能验证第 5 章的逐链路拥塞控制和第 6 章的拓扑发现。

## 9.6 实现前需要固定的条件

- **内核权限：** 创建 namespace、配置 qdisc 和读取部分接口状态需要 root 或 `CAP_NET_ADMIN`；容器中必须显式授予所需能力。
- **路径隔离：** 主动 UDP 探测、MPUDP 数据包和重传包都要绑定对应接口，防止被默认路由送到另一条链路。
- **MTU：** 每条路径分别探测 MTU，视频切片长度需要扣除 IP、UDP、MPUDP、AES-GCM 标签和隧道开销，避免 IP 分片放大丢包。
- **控制通道：** QUIC 控制消息需要记录其实际使用路径。实验可让控制通道使用稳定管理路径，但必须说明这与控制消息共享受损业务链路的真实场景存在差异。
- **时间同步：** 单机 namespace 共用系统时钟，可直接测量单向时延；多机实验需要 NTP/PTP，同步不可靠时只使用 RTT 和相对时间。
- **FEC 与重传：** 测试需要同时覆盖随机丢包和突发丢包，并记录 FEC 恢复、一次 NACK 重传、关键帧请求及 deadline 超时丢弃的先后关系。
- **安全测试：** 密钥和 nonce 不能写入抓包或普通日志；重放测试使用复制的旧包，篡改测试使用隔离的测试代理，不修改生产流量。
- **可重复性：** 保存内核版本、qdisc 参数、随机种子、视频样本、编码参数和程序版本，使不同算法结果可以复现。

## 9.7 分阶段验证路线

实验按以下顺序实施可以减少多个机制同时启用造成的定位困难：

1. 单链路验证 MPUDP 封装、AES-GCM、序号、CRC32C 和视频重组。
2. 三条无损链路验证策略路由、`path_id`、去重和乱序重排。
3. 分别注入丢包、延迟、抖动、重复、乱序、损坏和中断，验证检测准确性。
4. 启用 FEC、一次 NACK 和关键帧请求，比较恢复率与附加时延。
5. 启用逐链路拥塞控制和多路径调度，验证发送速率不超过安全容量。
6. 启用第 10 章链路评分，比较固定权重、轮询调度和质量感知调度的 QoE。
7. 最后在真实光纤、5G 和 Wi-Fi 设备上重复关键实验，验证仿真结论是否成立。
