# 第 4 章 传输协议

## 4.1 RTP/RTCP

RTP 是实时音视频传输协议，常与 UDP 配合使用。RTP 包头中的 sequence number、timestamp、payload type 和 SSRC 对视频流排序、同步和统计具有参考价值。

RTCP 可用于接收质量反馈，包括丢包、抖动和往返时延等信息。自定义聚合协议可以参考 RTP/RTCP 的设计思想。

## 4.2 GB/T 28181
GB/T 28181《公共安全视频监控联网系统信息传输、交换、控制技术要求》是我国公共安全视频监控系统中非常重要的联网标准，现行版本为 GB/T 28181-2022。该标准主要规定不同厂商、不同层级的视频监控设备和平台之间如何完成设备注册、目录查询、实时视频点播、录像回放、云台控制、报警通知以及平台级联等操作，从而实现跨设备、跨平台的视频监控系统互联互通。

在本项目中，GB/T 28181 可以作为前端监控设备接入聚合路由器的标准协议。监控摄像头首先通过 SIP 向聚合路由器或接入平台完成注册和状态维护；当系统需要获取某一路视频时，通过 SIP/SDP 建立媒体会话，随后摄像头通过 RTP/RTCP 将 H.264/H.265 视频流发送至聚合路由器。聚合路由器接收到视频后，再进行解析、加密、分片和多链路调度，并通过后续异构网络传输至聚合服务器。


## 4.3 GB/35114
GB 35114-2017《公共安全视频监控联网信息安全技术要求》是面向公共安全视频监控联网系统的信息安全标准，目前仍为现行国家标准。该标准主要针对视频监控系统联网过程中可能存在的身份冒用、非法设备接入、视频数据泄露以及信息被篡改等安全问题，对设备身份认证、系统接入认证、数据完整性保护和视频信息安全传输等方面提出要求。

在本项目中，GB 35114 可以作为“视频安全传输模块”的标准参考。对于监控摄像头采集的视频，在进入聚合路由器以及通过异构网络向聚合服务器传输时，可以参考该标准设计身份认证、视频数据加密、完整性校验和安全接入机制，从而保证视频数据在光纤、5G、Wi-Fi 等不同链路上传输过程中的机密性、完整性和可信性。


## 4.4 GA/T 1400.4
GA/T 1400.4-2017《公安视频图像信息应用系统 第4部分：接口协议要求》是面向公安视频图像信息应用系统的数据交换接口规范，目前属于现行的公安行业推荐性标准。该标准主要规定视频图像信息系统之间的接口类型、资源描述、消息交互和接口安全等内容，其接口主要包括采集接口、数据服务接口、级联接口和分析接口，并采用 REST 架构，通过 URI 对资源进行标识，支持基于 HTTP 的信息交换。

在本项目中，GA/T 1400.4 可以主要应用在聚合服务器和 AI Agent 后端。当聚合服务器恢复视频并由 AI Agent 完成人员、车辆、异常事件等视频内容分析后，可以按照 GA/T 1400.4 的接口形式，将分析得到的结构化信息、图片、视频片段、标签和告警信息上传到上层视频图像应用平台或数据库，也可以接受上层平台下发的分析任务。

## 4.6 MPTCP 基础

MPTCP 是 TCP 的多路径扩展，可通过多个子流同时传输数据。其优点是对应用透明、可靠性较好，但仍然继承 TCP 的有序交付和队头阻塞问题。

对于实时视频回传，MPTCP 可作为多链路传输的对比技术，但不一定是最低时延场景下的最优选择。

## 4.7 MPUDP 基础

MPUDP 通常不是单一标准协议，而是指基于 UDP 构建的多路径传输机制。其典型做法是在 UDP 之上自定义聚合协议头，并由聚合路由器根据链路状态将视频数据分发到多条链路。

MPUDP 的优势是灵活、低时延、可控制性强，适合实现链路质量感知、包级调度、乱序重排、FEC、NACK、关键帧冗余和实时丢弃策略。

其主要不足是可靠性、拥塞控制、乱序处理和安全机制需要自行设计，工程复杂度高于直接使用成熟协议。

## 4.8 SCTP 基础

SCTP 是一种独立传输层协议，支持多流、多宿主、可靠传输和消息边界保持。与 TCP 相比，SCTP 的多流能力可以降低部分队头阻塞影响，多宿主能力可以用于链路故障切换。

但 SCTP 在公网环境中的部署普及度不如 TCP/UDP，NAT 和防火墙穿透也更复杂。在本课题中，SCTP 更适合作为控制信令、链路状态上报和设备管理通道，而不是视频数据主通道。

## 4.9 MPTCP、MPUDP、SCTP 用法对比

| 协议 | 核心定位 | 优点 | 局限 | 推荐用途 |
|---|---|---|---|---|
| MPTCP | 可靠多路径 TCP | 对应用透明、内核支持、可靠传输、链路容灾 | 队头阻塞、重传等待、调度不易自定义 | 对比方案、文件/日志回传、非强实时数据 |
| MPUDP | 自定义低时延多路径 UDP | 灵活、低时延、适合包级调度和视频感知传输 | 需要自行处理可靠性、拥塞和乱序 | 视频数据主通道、核心实验方案 |
| SCTP | 多流多宿主可靠传输 | 消息边界、多流、多宿主、适合信令 | 公网部署受限、视频生态较弱 | 控制信令、状态上报、设备管理 |

面向无人机、无人车实时图像回传，推荐采用如下分工：

```text
主要测试 数据面：MPUDP
控制面：TCP / QUIC / SCTP
对比方案：MPTCP
```

## 4.10 基于 MPUDP 的视频流传输处理

MPUDP 适合作为本实验模型的视频数据主通道。它基于 UDP 构建多路径传输机制，由聚合路由器自主完成包级调度、链路选择、冗余控制和发送速率控制。

### 4.10.1 MPUDP 发送流程

基于 MPUDP 的视频发送流程如下：

```text
视频输入
  ↓
解封装 / 码流解析
  ↓
添加 flow_id、seq、timestamp、frame_type
  ↓
按 MTU 分包
  ↓
链路质量评估
  ↓
包级调度
  ↓
不同 UDP socket 绑定不同链路发送
```

聚合路由器可以为每条链路维护独立 UDP socket，并通过源 IP 绑定、策略路由或 `SO_BINDTODEVICE` 控制数据包从指定接口发出。

### 4.10.2 MPUDP 调度策略

MPUDP 可以支持多种调度方式：

- 单链路模式：只使用当前质量最好的链路。
- 主备模式：主链路异常时切换到备用链路。
- 轮询模式：按顺序将视频包分配到不同链路。
- 加权调度：按链路带宽、时延、丢包和抖动设置发送比例。
- 视频感知调度：I 帧或关键数据走高质量链路，普通帧按比例分发。
- 冗余调度：关键帧、头信息或控制数据复制到多条链路。

由于 MPUDP 不依赖传输层有序交付，服务器端必须处理乱序、重复和丢包。其优势是低时延和灵活性，适合无人机、无人车实时视频回传实验。

### 4.10.3 MPUDP 服务器恢复

聚合服务器接收 MPUDP 数据后，需要执行：

- 解析聚合包头。
- 按 flow_id 区分视频流。
- 根据 seq 去重和排序。
- 根据 frame_id、frag_index、frag_count 重组视频帧。
- 根据 timestamp 判断过期包。
- 根据 gap detection 发现丢包。
- 根据 FEC 或 NACK 机制尝试恢复。
- 恢复为 RTP/UDP、MPEG-TS、WebRTC、RTMP 或文件输出。

MPUDP 的重点是让服务器端掌握足够的包级信息，从而在多链路乱序条件下恢复连续可用的视频流。

### 4.10.4 MPUDP 与实际链路的结合方式

在实际无人平台部署中，MPUDP 不只是“多条 UDP 链路同时发送”，而是要把每条链路的实际角色纳入调度。

无人机场景可采用如下方式：

```text
5G/4G 公网链路：承担主要视频包，带宽充足时优先使用
专网链路：承担关键帧、控制相关画面或公网弱覆盖时的接管链路
卫星链路：作为低码率兜底链路，保障极端场景下仍有画面
```

无人车场景可采用如下方式：

```text
多运营商 5G/4G：分担主视频流，降低单运营商覆盖盲区风险
Wi-Fi / Wi-Fi Mesh：园区、港口、仓库内承担高带宽近距离回传
专网 / Mesh 电台：任务区域内提供稳定辅助链路
```

MPUDP 调度器可根据实际链路状态动态调整视频包分配。例如前视主摄像头的 I 帧可以优先走当前 RTT 较低、丢包较少的链路；环视或辅助摄像头的普通帧可以走带宽较大但波动更明显的链路；当某条链路进入 DEGRADED 或 FAILED 状态时，调度器立即降低其权重或停止向该链路发送实时视频包。

## 4.11 基于 MPTCP 的辅助传输与对比处理

MPTCP 在本实验模型中不作为实时视频数据面的主方案，而是作为辅助传输和对比方案。它在内核层将一个 TCP 连接拆分为多个子流，通过多条链路传输。应用层看到的仍然是普通 TCP 连接。

### 4.11.1 MPTCP 辅助传输方式

基于 MPTCP 的辅助传输可以采用以下方式：

- 将非强实时数据封装为 TCP 流，如任务日志、设备状态、诊断文件、低频截图和回放文件。
- 对照实验中，可将同一路视频封装为基于 TCP 的协议，如 RTSP over TCP、RTMP/FLV 或自定义 TCP 流。
- 在支持 MPTCP 的 Linux 内核上开启 MPTCP。
- 聚合路由器和聚合服务器之间建立一个 MPTCP 连接。
- 内核根据可用链路建立多个 TCP subflow。
- 应用层按普通 TCP socket 读写数据。

其逻辑如下：

```text
辅助数据 / 对比视频流
  ↓
普通 TCP socket
  ↓
MPTCP 内核协议栈
  ├── 5G subflow
  ├── Wi-Fi subflow
  └── 专网 subflow
  ↓
聚合服务器 TCP 接收流
```

### 4.11.2 MPTCP 对实时视频的影响

MPTCP 的优势是可靠、有序、对应用透明，不需要聚合路由器显式处理每个包走哪条链路。但它也会带来实时视频场景中的典型问题：

- TCP 有序交付可能造成队头阻塞。
- 丢包后等待重传会增加时延。
- 不同链路 RTT 差异过大时，慢路径可能拖累整体输出。
- 应用层较难直接控制某个视频帧走哪条链路。
- 不适合灵活实现关键帧冗余、帧级 deadline 和实时丢弃策略。

因此，MPTCP 更适合作为可靠辅助通道和对比基线，用于和 MPUDP 比较吞吐、时延、卡顿、丢包恢复和链路故障切换效果。实际系统中，MPTCP 可承担日志、配置、任务文件、低频图像和非实时记录流，避免把强实时视频主链路交给有序可靠传输机制。

### 4.11.3 MPUDP 与 MPTCP 的分工

在本课题中，两者可按以下方式定位：

| 传输方式 | 适用角色 | 视频流处理特点 |
|---|---|---|
| MPUDP | 实时视频数据主方案 | 聚合路由器显式分包、标识、调度，服务器显式去重、重排、恢复 |
| MPTCP | 辅助可靠通道和对比方案 | 应用层按连续字节流处理，内核负责多路径，可靠但可能增加时延 |

对于实时图像回传，建议优先研究 MPUDP，因为它更便于体现异构链路下的视频业务感知传输。MPTCP 则用于说明传统可靠多路径传输在实时视频中的优势和局限，并承担系统中的辅助可靠传输任务。

## 4.12 聚合服务器端恢复输出

实时视频流主要经过 MPUDP 到达聚合服务器后，需要恢复为后续系统可使用的视频形式。MPTCP 到达服务器的数据以辅助数据或对比实验流为主，处理逻辑相对简单。

### 4.12.1 MPUDP 恢复输出

MPUDP 场景下，服务器需要先完成包级恢复，再输出媒体流：

```text
多链路 UDP 接收
  ↓
解析聚合包头
  ↓
按 flow_id 分类
  ↓
去重、排序、丢包检测
  ↓
按 frame_id 和分片信息重组
  ↓
恢复 RTP / MPEG-TS / H.264/H.265 码流
  ↓
输出到播放器、流媒体服务器或文件
```

输出方式可包括 UDP/RTP、MPEG-TS/UDP、SRT、RTMP、WebRTC 或文件存储。实验阶段可优先输出为 MPEG-TS/UDP 或文件，便于验证和分析。

### 4.12.2 MPTCP 辅助数据恢复输出

MPTCP 场景下，服务器侧应用层收到的是可靠有序字节流，因此不需要像 MPUDP 那样显式处理包级乱序。对于辅助数据，服务器主要完成文件接收、日志入库、状态解析和任务记录保存；对于对比实验视频流，则需要完成视频协议层的解析和输出。

典型处理包括：

- 从 TCP 字节流中解析日志、状态消息、文件块，或在对比实验中解析 RTSP、RTMP/FLV、自定义帧边界、MPEG-TS 数据。
- 恢复媒体时间戳。
- 检查码流连续性。
- 输出到播放器、流媒体服务器或文件。

MPTCP 的服务器恢复逻辑较简单，但时延可控性较弱。因此在评价时应重点观察其作为对比视频链路时，是否因为重传等待和队头阻塞导致视频卡顿。

## 4.13 本章小结

本章先说明 RTP/RTCP、GB/T 28181、GB 35114、GA/T 1400.4、SIP、MPTCP、MPUDP 和 SCTP 等协议基础，再进一步展开聚合路由器到聚合服务器之间的视频流传输处理过程。

在本实验模型中，实时视频数据面以 MPUDP 为主，由聚合路由器完成视频包封装、链路质量评估和包级调度，由聚合服务器完成去重、排序、丢包检测、分片重组和媒体流恢复。MPTCP 作为辅助可靠通道和对比方案，主要用于日志、状态、文件、低频图像以及非强实时视频流的传输。
