# 第 5 章 多路径视频传输差错控制与安全机制

本章在既有技术路线基础上，固定聚合路由器到聚合服务器之间的数据保护、差错检测和恢复方案。系统以 MPUDP 作为视频数据主通道，以可靠且加密的 QUIC 通道传递链路反馈、NACK 和密钥协商等控制信息；MPTCP 仅作为对比方案，SCTP 保留为辅助研究方案。

整体协议关系如下：

```text
监控摄像头
    │
    ├── GB/T 28181：SIP/SDP 注册、控制和会话建立
    ├── RTP/RTCP：视频传输与质量反馈
    └── GB 35114：身份认证、安全接入和数据保护要求
    │
    ▼
聚合路由器
    │
    ├── RTP/PS/H.264/H.265 解析
    ├── 视频切片、FEC 编码、AES-256-GCM 加密
    ├── MPUDP：多路径视频数据传输
    └── QUIC：反馈、NACK、密钥协商和链路控制
    │
    ▼
光纤 / 5G / Wi-Fi / 卫星 / 专网 / 公网
    │
    ▼
聚合服务器
    │
    ├── 差错与篡改检测、解密、防重放
    ├── 去重、乱序重排、FEC 恢复和选择性重传
    ├── 视频帧重组、关键帧请求和 QoE 统计
    └── GA/T 1400.4：向 AI Agent 或上层平台提供数据接口
```

## 5.1 需要处理的问题

异构链路具有不同的带宽、时延、抖动和丢包特性。同一路视频被拆分到多条链路传输后，聚合服务器必须处理以下问题：

| 问题 | 主要原因 | 影响 |
|---|---|---|
| 丢包 | 无线信号波动、网络拥塞、队列溢出或链路中断 | 视频帧不完整、花屏、卡顿或解码失败 |
| 链路差错 | 噪声、截断、错误封装或数据位翻转 | 校验和错误、载荷损坏 |
| 数据篡改 | 非法节点修改包头或视频载荷 | 画面失真、伪造数据进入 AI 分析系统 |
| 数据窃听 | 攻击者监听公网、Wi-Fi 等传输链路 | 敏感视频内容泄露 |
| 乱序 | 多条链路时延不同或路由发生变化 | 视频切片无法直接按到达顺序重组 |
| 重复 | 跨链路冗余、网络复制或发送端重传 | 浪费缓存和处理资源，可能造成重复输出 |
| 重放 | 攻击者重新发送以前截获的合法数据包 | 旧画面或旧控制信息被错误接收 |

## 5.2 协议与安全方案选型

本项目固定采用以下方案：

| 功能 | 固定方案 | 用途 |
|---|---|---|
| 视频数据面 | 自定义 MPUDP | 将视频切片按策略发送到多条异构链路 |
| 控制与反馈面 | QUIC | 可靠传递 NACK、链路统计、密钥协商和关键帧请求，利用 TLS 1.3 保护控制信息 |
| 视频切片加密 | AES-256-GCM | 防止视频载荷被读取或窃听，同时检测篡改 |
| 随机差错快速检测 | CRC32C | 快速发现包头、密文或认证标签的传输差错，并形成链路差错统计 |
| 身份认证 | 设备证书和双向认证 | 阻止未授权聚合路由器或服务器接入 |
| 防重放 | 会话标识、全局序列号和滑动窗口 | 拒绝已经接收或明显过期的数据包 |
| 丢包恢复 | FEC 优先，NACK 选择性重传补充 | 在恢复能力和实时性之间取得平衡 |
| 解码恢复 | RTCP PLI/FIR 请求关键帧 | 参考帧链无法恢复时使解码器重新同步 |
| 拥塞控制 | 每条链路独立的时延、丢包和 ECN 混合控制 | 限制发送速率和在途数据，避免路由器主动造成排队与丢包 |

CRC32C 只负责发现随机传输差错，不能用于判断恶意篡改。防篡改、防读取和防窃听由 AES-256-GCM 提供：视频切片以密文形式传输，接收端只有在认证标签校验成功后才能接受并解密数据。自定义包头中参与路由所必需的字段可以保持明文，但必须作为附加认证数据（AAD）纳入 GCM 完整性保护，防止字段被修改。

## 5.3 视频切片包头

聚合路由器完成 RTP/PS/H.264/H.265 解析后，对视频数据进行分片，并为每个数据切片和 FEC 切片增加统一 MPUDP 包头。建议固定以下字段：

| 字段 | 作用 |
|---|---|
| `magic`、`version`、`header_len` | 识别协议并支持包头扩展 |
| `session_id` | 区分设备重新连接或重新协商后的传输会话 |
| `stream_id` | 区分摄像头和视频流 |
| `packet_seq` | 会话内单调递增的全局包序号，用于丢包、乱序和重放检测 |
| `frame_id` | 标识切片所属的视频帧 |
| `slice_id`、`slice_count` | 标识帧内切片位置并判断视频帧是否完整 |
| `frame_type` | 标识 I 帧、P 帧或其他帧类型 |
| `flags` | 标识关键帧、FEC 包、重传包和控制状态 |
| `send_timestamp`、`deadline` | 计算时延并判断数据是否已经失去播放价值 |
| `path_id` | 标识实际使用的光纤、5G、Wi-Fi 等发送链路 |
| `fec_group_id`、`fec_index`、`fec_k`、`fec_r` | 标识 FEC 分组、分片位置、原始片数和冗余片数 |
| `payload_len` | 校验载荷长度并防止越界解析 |
| `key_epoch` | 标识当前会话使用的密钥版本 |
| `crc32c` | 对包头、密文和认证标签进行随机差错快速检测 |
| `auth_tag` | AES-256-GCM 认证标签，用于验证完整性并检测篡改 |

每个视频切片必须具有唯一的逻辑身份，即 `session_id + stream_id + frame_id + slice_id`。每次发送还必须具有唯一的 `packet_seq`。同一切片发生重传时，保留原有 `frame_id` 和 `slice_id`，但使用新的 `packet_seq` 和 GCM nonce 并重新加密，从而避免 nonce 重用。

## 5.4 发送端封装与保护流程

聚合路由器按照以下固定顺序处理视频数据：

1. 接收并解析摄像头通过 GB/T 28181 会话传来的 RTP/PS/H.264/H.265 视频流。
2. 识别帧边界和帧类型，为 I 帧和其他参考帧设置较高优先级。
3. 按照路径 MTU 对视频帧进行切片，保证加入 MPUDP、UDP、IP 和隧道包头后不触发 IP 分片。
4. 将若干原始切片组成 FEC 分组并生成冗余切片。初始实验参数采用 `k=10、r=2`，即 10 个原始切片配 2 个冗余切片，后续根据链路丢包率自适应调整冗余比例。
5. 为每个原始切片和 FEC 切片生成包头、唯一序列号及唯一 nonce，使用 AES-256-GCM 分别加密和认证。
6. 计算 CRC32C，并根据链路质量、帧重要性和截止时间选择发送路径。
7. 通过 MPUDP 发送视频数据，同时通过 QUIC 控制通道接收服务器反馈。

AES-256-GCM 的密钥由经过双向认证的 QUIC 控制通道协商或安全下发，并通过 `key_epoch` 标识版本。nonce 可由会话随机前缀与 `packet_seq` 组合生成，在同一密钥生命周期内禁止重复使用。密钥应按时间或流量阈值轮换，设备断线重连后必须建立新的 `session_id` 和会话密钥。

## 5.5 聚合服务器检测流程

服务器只允许通过全部检查的数据进入视频重排和重组模块，处理顺序固定如下：

1. **基本合法性检查：** 检查来源会话、协议版本、包头长度、载荷长度和字段取值范围，过短、超长或格式非法的数据包直接丢弃。
2. **CRC32C 检查：** 快速检测随机比特差错。校验失败时丢弃数据包，并增加对应 `path_id` 的链路差错计数。
3. **防重放预检查：** 检查 `session_id`、`key_epoch` 和 `packet_seq` 是否处于允许的接收窗口。明显过期的数据包直接丢弃，但在认证成功前不得推进接收窗口。
4. **GCM 认证与解密：** 使用包头关键字段作为 AAD 验证认证标签。认证失败的数据包按篡改或密钥异常处理，记录安全事件并丢弃；禁止把未认证数据交给 FEC、解码器或 AI Agent。
5. **更新防重放窗口：** 只有认证成功后才能记录 `packet_seq` 并推进滑动窗口，防止伪造的大序号数据包破坏接收状态。
6. **重复检测：** 相同 `packet_seq` 再次出现时按网络重复包丢弃；逻辑身份相同但序号不同的数据包按重传副本处理，只保留第一份有效数据。
7. **乱序与丢包检测：** 序号大于期望值的数据包进入重排窗口；发现序号缺口或帧内切片不完整时，启动短时等待和丢包恢复流程。

异常判定规则如下：

| 异常 | 判定依据 | 服务器动作 |
|---|---|---|
| 丢包 | `packet_seq` 出现缺口，或超过等待时间后 `slice_count` 仍不完整 | 尝试 FEC，必要时发送 NACK |
| 链路差错 | 长度异常或 CRC32C 失败 | 丢弃并增加该链路差错计数 |
| 篡改 | GCM 认证标签验证失败 | 丢弃、记录安全事件，连续发生时隔离会话或链路 |
| 窃听 | 无法由接收端直接检测 | 通过 AES-256-GCM 加密使截获者无法读取视频内容 |
| 乱序 | 合法序号位于期望序号之后且仍在接收窗口内 | 放入重排缓冲区等待缺失包 |
| 重复 | `packet_seq` 已接收，或逻辑切片身份已完成 | 丢弃重复副本，不重复输出 |
| 重放 | 序号已确认接收、早于窗口下界或会话已经失效 | 丢弃并记录重放计数 |

## 5.6 乱序重排与丢包恢复

### 5.6.1 乱序重排

每一路视频流维护独立的滑动接收窗口、哈希去重表和抖动缓冲区。服务器按照 `packet_seq` 判断网络到达顺序，按照 `frame_id + slice_id` 完成视频帧重组。实验初始值采用 256 个包的接收窗口和 50 ms 的最大重排等待时间，后续可根据实测 RTT 和抖动调整。

到达时间超过 `deadline` 的切片直接丢弃，不因等待顺序完整而无限增加视频时延。不同视频流的窗口必须相互独立，防止一路视频异常阻塞其他视频流。

### 5.6.2 FEC 前向纠错

发现缺失切片后，服务器首先检查对应 FEC 分组。如果任意 `k` 个有效原始或冗余切片已经到达，则立即恢复缺失数据，不请求重传。FEC 恢复出的数据只能来自已经通过 GCM 认证的分组切片，恢复完成后再进入视频帧重组模块。

I 帧和重要参考帧可以采用更高冗余比例或跨链路发送冗余片；普通 P 帧采用基础冗余比例。服务器持续统计每条链路的丢包率，并通过 QUIC 控制通道通知聚合路由器调整 `fec_r`。

### 5.6.3 NACK 选择性重传

当 FEC 无法恢复缺失切片时，服务器只对仍具有播放价值的数据发送 NACK。是否重传采用以下固定条件：

```text
预计重传到达时间 = 当前时间 + 平滑 RTT + 处理裕量

预计重传到达时间 < 视频帧 deadline：发送 NACK
预计重传到达时间 >= 视频帧 deadline：放弃重传
```

实时视频默认只进行一次选择性重传，避免多次等待造成时延持续累积。聚合路由器收到 NACK 后，优先选择当前丢包率更低、预计到达时间更短的链路重传。重传包使用新的 `packet_seq` 和 nonce，但保留原切片的逻辑身份。

### 5.6.4 关键帧请求

请求新关键帧不是普通丢包的第一处理方式。只有出现以下任一情况时，服务器才触发关键帧请求：

- 丢失的 I 帧在 FEC 和一次选择性重传后仍无法恢复。
- 连续参考帧损坏，解码器报告参考链已经失效。
- 视频流长时间无法形成可解码画面或会话刚完成切换恢复。

服务器通过 QUIC 控制通道将关键帧请求发送给聚合路由器，再由聚合路由器通过 RTCP PLI 请求编码器尽快产生关键帧；编码器或会话需要完全重新同步时才使用 RTCP FIR。关键帧请求应设置最短时间间隔，实验初始值为 1 秒，防止频繁产生 I 帧导致码率突增和网络拥塞。

### 5.6.5 超时丢弃与错误隐藏

如果缺失切片无法在 `deadline` 前恢复，服务器停止等待并丢弃不完整帧。非关键帧损坏时可由解码器采用上一帧复制、运动补偿等错误隐藏方法减轻画面跳变；参考链已经失效时直接请求新关键帧，避免错误持续传播。

恢复优先级固定为：

```text
短时乱序等待
    ↓
FEC 本地恢复
    ↓
满足截止时间时发送一次 NACK
    ↓
参考链失效时请求新关键帧
    ↓
超过截止时间后丢弃并执行错误隐藏
```

## 5.7 链路反馈与调度联动

聚合服务器按照 `path_id` 分别统计以下指标：

- 接收包数、有效包数和吞吐量。
- 丢包率、CRC 差错率、认证失败率和重复率。
- 乱序包比例、最大乱序深度和重排等待时间。
- 单向传输时延、RTT 和抖动。
- FEC 恢复率、NACK 次数、重传成功率和过期包比例。
- I 帧恢复时间、卡顿次数和视频可解码率。

服务器通过 QUIC 控制通道向聚合路由器周期性反馈链路质量。某条链路出现持续高丢包、高差错或高时延时，聚合路由器降低该链路的调度权重；链路完全不可用时停止分配视频切片；链路恢复并通过探测后再逐步提高权重。认证失败率异常升高时按安全事件处理，不能仅通过增加 FEC 或重传掩盖。

## 5.8 多链路拥塞控制与 QoE 联动

MPUDP 基于 UDP，不具备 TCP、QUIC 自带的拥塞控制能力。如果聚合路由器只按照网卡标称速率持续发送，数据会在本机队列、运营商网络或服务器入口处堆积，最终表现为时延上升、抖动增大、突发丢包和视频卡顿。因此，聚合路由器必须对每条链路分别维护拥塞状态，并在多路径调度之前限制实际发送速率。

### 5.8.1 拥塞状态来源

每条链路的拥塞控制器同时使用发送端和接收端信息：

| 信息来源 | 指标 | 作用 |
|---|---|---|
| 聚合路由器本地 | socket/qdisc 队列长度、发送失败、网卡速率、在途字节数 | 发现本地排队和接口过载 |
| 聚合服务器 ACK | 已接收序号、接收时间、累计接收字节数 | 估计交付速率、RTT、丢包和在途数据 |
| 聚合服务器链路统计 | 单向时延、抖动、乱序、过期包比例 | 判断链路是否仍适合实时视频 |
| IP/网络反馈 | ECN 标记、不可达消息、路径 MTU 变化 | 尽早发现网络拥塞或路径变化 |

CRC 错误、GCM 认证失败和网络拥塞必须分别统计。CRC 或认证失败说明数据损坏或安全异常，不能直接当作拥塞信号；只有序号缺口、RTT 上升、ECN 标记、交付速率下降和持续排队等信息共同出现时，才判定链路发生拥塞。

### 5.8.2 每条链路独立控制

光纤、5G 和 Wi-Fi 的容量与 RTT 差异较大，不能共用一个拥塞窗口。聚合路由器为每个 `path_id` 独立维护以下状态：

```text
min_rtt          链路无明显排队时的基准 RTT
smoothed_rtt     平滑 RTT
delivery_rate    服务器实际确认的交付速率
pacing_rate      当前允许的平滑发送速率
cwnd             当前允许的最大在途字节数
bytes_in_flight  已发送但尚未确认的字节数
loss_rate        滑动窗口内的网络丢包率
ecn_rate         ECN 拥塞标记比例
queue_delay      smoothed_rtt - min_rtt
```

数据包只有同时满足以下两个条件才能进入某条链路：

```text
该链路 bytes_in_flight + packet_size <= cwnd
当前发送时刻符合该链路 pacing_rate 的节奏
```

发送端使用 pacing 定时器平滑发包，禁止一次性把一帧的全部切片突发写入网卡队列。初始阶段以较低速率探测可用容量；链路稳定且队列时延较低时缓慢提高 `pacing_rate`；出现 ECN、RTT 持续膨胀或连续丢包时立即降低 `pacing_rate` 和 `cwnd`；链路中断时把该路径状态置为不可用，恢复后重新从保守速率开始探测。

### 5.8.3 多路径总速率约束

多路径可用带宽不能全部分配给原始视频数据，还必须为 FEC、重传和控制报文预留空间。发送预算固定按下式约束：

```text
视频原始码率
+ FEC 冗余码率
+ 预计重传码率
+ 控制报文开销
<= 各可用链路安全发送速率之和
```

单条链路的安全发送速率以其 `delivery_rate`、`cwnd / smoothed_rtt` 和接口能力中的最小值为基础，并保留安全余量。实验初始阶段可只使用估计可用容量的 85%，剩余部分用于吸收无线链路波动和突发重传。

多路径调度器根据链路的安全发送速率分配权重，但不能只追求总吞吐量。具有较短 deadline 的关键视频切片优先进入低时延、低丢包链路；普通 P 帧切片可以进入容量较大但时延略高的链路；卫星等高 RTT 链路优先承担非紧急数据、FEC 冗余或兜底传输。任何路径都不得突破自身 `pacing_rate` 和 `cwnd`。

### 5.8.4 拥塞时的视频自适应

当各链路安全发送速率之和小于当前视频总码率时，仅调整调度权重无法消除拥塞，聚合路由器必须与视频业务联动，处理优先级固定如下：

1. 停止增加 FEC 冗余，并根据实际丢包原因调整冗余比例，避免拥塞越严重、冗余流量越多。
2. 取消已经超过 deadline 的重传任务和待发送切片。
3. 降低非关键 P 帧或 B 帧的发送优先级，必要时主动丢弃增强层或低优先级帧。
4. 通过编码器接口降低码率、分辨率或帧率，使输入速率回落到安全发送预算以内。
5. 保留 I 帧、重要参考帧和控制消息的传输机会，并为关键帧设置请求冷却时间，避免连续关键帧进一步加重拥塞。

容量恢复后应逐步提升视频码率，不能立即恢复到原始高码率，否则容易产生新的排队和振荡。编码码率调整周期应明显长于包级调度周期：包级控制负责毫秒级平滑发包，编码器负责秒级画质调整。

### 5.8.5 对视频 QoE 的影响

拥塞控制直接影响视频 QoE，主要关系如下：

| 控制结果 | 对 QoE 的影响 |
|---|---|
| 发送速率长期高于链路容量 | 排队时延、抖动和丢包持续增加，引起卡顿、花屏及关键帧恢复 |
| 降速过慢 | 拥塞队列无法及时排空，过期包和无效重传增多 |
| 降速过度 | 丢包减少，但视频码率和清晰度不必要地下降 |
| 频繁升降速 | 编码质量波动，调度权重振荡，用户观看体验不稳定 |
| 合理 pacing 和截止时间丢弃 | 减少突发丢包和无效等待，降低端到端时延 |
| 视频优先级感知调度 | 在相同带宽下优先保证关键帧，提高连续可解码率 |

系统不应只以吞吐量评价拥塞控制效果，还应联合统计端到端时延、95/99 分位时延、抖动、过期包比例、卡顿次数、关键帧恢复时间、可解码帧率、PSNR、SSIM 和 VMAF。最终目标是在可接受的清晰度下降范围内优先保持低时延和连续播放，而不是单纯把链路带宽占满。

## 5.9 完整处理路线

```text
摄像头视频
    │  GB/T 28181 + RTP/RTCP
    ▼
聚合路由器解析视频帧并判断帧类型
    │
    ▼
按 MTU 切片 → FEC 分组与冗余编码 → 增加 MPUDP 包头
    │
    ▼
AES-256-GCM 加密与认证 → CRC32C → 多路径 MPUDP 调度发送
    │
    ▼
光纤 / 5G / Wi-Fi / 卫星 / 专网 / 公网
    │
    ▼
聚合服务器多链路接收
    │
    ▼
格式检查 → CRC32C → 防重放预检查 → GCM 认证与解密
    │
    ▼
去重 → 乱序缓存与重排 → 丢包和截止时间判断
    │
    ├── FEC 可恢复：恢复缺失切片
    ├── 可在截止时间前重传：通过 QUIC 发送一次 NACK
    ├── 参考链失效：通过 RTCP PLI/FIR 请求新关键帧
    └── 已超过截止时间：丢弃并执行错误隐藏
    │
    ▼

    └── GA/T 1400.4 → 视频图像应用平台
```

## 5.10 实验验证要求

可使用 Linux network namespace、Docker 和 `tc netem` 分别注入随机丢包、突发丢包、延迟、抖动、乱序、重复和比特差错，对本章方案进行验证。篡改、窃听和重放场景应通过测试程序主动修改、截获或重新发送 MPUDP 数据包构造。

实验至少记录以下结果：

- 各类异常的检测准确率和误判率。
- 不使用恢复、仅使用 FEC、仅使用重传以及 FEC 加重传时的恢复率。
- 不同重排窗口对端到端时延和有效丢包率的影响。
- I 帧丢失后触发关键帧请求并恢复正常解码所需时间。
- 开启 AES-256-GCM、CRC32C 和 FEC 前后的 CPU、内存、带宽和时延开销。
- 非法篡改包、重复包和重放包是否被稳定拒绝。
- 不同链路质量下的 PSNR、SSIM、VMAF、卡顿次数和端到端时延。

通过上述实验，可以验证差错检测、安全保护和恢复机制是否能够在异构网络中同时满足视频机密性、完整性、可用性和实时性要求。
