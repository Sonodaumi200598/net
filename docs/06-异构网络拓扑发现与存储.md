# 第 6 章 异构网络拓扑发现与存储

本章研究范围限定为聚合路由器、光纤/5G/Wi-Fi 等异构传输链路和聚合服务器，不展开摄像头内部网络及服务器之后的 AI Agent 和视频图像应用平台。拓扑管理的目标不是还原运营商内部所有物理设备，而是建立一张可用于 MPUDP 调度、拥塞控制、故障切换和实验分析的逻辑传输拓扑。

本项目中的目标拓扑如下：

```text
                         聚合路由器
                    Link Monitor / Scheduler
                              │
                            MPUDP
                              │
             ┌────────────────┼────────────────┐
             │                │                │
          光纤链路           5G 链路         Wi-Fi 链路
          path_fiber         path_5g          path_wifi
             │                │                │
             └────────────────┼────────────────┘
                              │
                           异构网络
                              │
                              ▼
                         聚合服务器
                 Receiver / Reorder / FEC / NACK
```

## 6.1 拓扑能够发现到什么程度

系统可以稳定获取以下逻辑拓扑信息：

- 聚合路由器有哪些网络接口，以及接口类型、MAC 地址、IP 地址、MTU 和工作状态。
- 每个接口使用的默认网关、策略路由表、源地址和出口规则。
- 每条逻辑路径对应的 `path_id`、本地接口、服务器入口地址和会话状态。
- 聚合服务器实际观察到的源 IP、源端口和 NAT 映射。
- 每条路径是否可达，以及 RTT、时延、抖动、丢包、可用带宽和路径 MTU。
- 在网络允许响应时，通过受控 traceroute 获得的部分三层跳点。

系统通常不能完整获知运营商 5G 核心网、MPLS、NAT、负载均衡或云网络内部的真实物理拓扑。中间路由器可能不响应 ICMP，多个逻辑跳点也可能隐藏在同一运营商网络中。因此，本项目将“聚合路由器接口到聚合服务器入口的一条可测量路径”视为一条逻辑边，中间跳点只作为可选诊断信息，不作为多路径调度成立的前提。

## 6.2 拓扑获取方式选择

拓扑采用“静态配置发现 + 主动探测 + 自有业务流被动测量”三种方式组合获取，不使用全网数据包嗅探作为主要方案。

| 获取方式 | 获取内容 | 是否作为核心方案 |
|---|---|---|
| Linux Netlink 和路由表读取 | 网卡、地址、MTU、网关、策略路由及接口上下线事件 | 是 |
| 认证 UDP 探测包 | 路径可达性、RTT、丢包、抖动和 NAT 映射 | 是 |
| MPUDP 数据与 QUIC ACK | 真实业务交付速率、序号缺口、乱序、过期包和拥塞状态 | 是 |
| ICMP ping | 基础可达性和辅助 RTT | 辅助 |
| traceroute/Paris traceroute | 可响应的三层跳点和路径变化 | 按需诊断 |
| libpcap/eBPF 嗅探 | 本机自有流量的包长、方向和时间戳统计 | 可选验证 |

单纯嗅探存在以下限制：只能观察经过本机的数据，无法看到没有产生流量的备用链路；加密后无法读取业务内容；无法可靠还原运营商内部拓扑；全量抓包还会带来性能、存储和隐私风险。因此，嗅探只用于实验调试或采集本机自有流量的元数据，不抓取和长期保存视频载荷。

## 6.3 聚合路由器本地发现

聚合路由器启动后，Link Monitor 首先通过 Linux Netlink 获取当前网络状态，并订阅后续变化事件。需要读取的信息包括：

```text
ip link       接口名称、类型、MAC、MTU、UP/DOWN 状态
ip addr       IPv4/IPv6 地址、前缀长度和地址生命周期
ip route      默认网关、路由下一跳和出接口
ip rule       源地址、fwmark 与策略路由表的对应关系
ethtool       有线接口速率及链路状态
无线/蜂窝接口  Wi-Fi 信号、5G 注册状态、信号质量和运营商信息
```

系统为每个可以独立到达聚合服务器的出口分配稳定 `path_id`。`path_id` 不直接使用临时 IP 地址，而由设备 ID、接口标识、链路类型和配置编号生成，避免 DHCP 地址改变后产生一条完全无关的新路径。

本地发现得到的只是“可能存在的链路”。接口处于 UP 状态不代表服务器一定可达，因此每条路径还必须完成端到端主动探测。

## 6.4 主动网络探测

### 6.4.1 认证 UDP 探测包

聚合路由器通过每条接口对应的源地址和策略路由表，分别向聚合服务器的探测端口发送轻量 UDP 探测包。探测包沿用 MPUDP 会话的身份认证和防重放机制，至少包含：

| 字段 | 作用 |
|---|---|
| `session_id`、`path_id` | 标识设备会话和被测链路 |
| `probe_seq` | 计算丢包和防止重复统计 |
| `send_timestamp` | 计算 RTT 或单向时延 |
| `payload_size` | 进行路径 MTU 和不同包长测试 |
| `nonce`、`auth_tag` | 防止伪造、篡改和重放探测结果 |

服务器收到探测包后返回原序号、服务器接收时间和服务器观察到的源地址/端口。路由器据此判断端到端可达性、RTT、抖动、探测丢包率和 NAT 映射。探测必须绑定指定源 IP 或 `SO_BINDTODEVICE`，并配合 `ip rule` 和独立路由表，防止所有探测包实际走同一个默认出口。

### 6.4.2 探测频率

探测频率按链路状态控制，避免探测流量本身造成拥塞：

| 链路状态 | 探测方式 |
|---|---|
| 正在传输 MPUDP 视频 | 主要使用真实业务 ACK，低频探测包只负责保活 |
| 空闲但可用 | 每 1 秒发送一次轻量保活探测 |
| 疑似中断 | 短时间连续探测 3 次，全部失败后标记为不可用 |
| 已中断 | 使用退避策略降低探测频率，恢复成功后逐步增加发送权重 |
| 地址、网关或路由发生变化 | 立即重新探测并创建新的路径版本 |

这些数值作为实验初始配置，应做成可调参数。实际部署时需要根据卫星、5G、Wi-Fi 等不同链路的 RTT、流量费用和功耗分别设置。

### 6.4.3 跳点和路径 MTU 探测

traceroute 只在会话建立、路径发生明显变化或人工诊断时执行，不持续高频运行。为了降低负载均衡导致的虚假路径变化，可以使用固定五元组或 Paris traceroute 思路保持探测流一致。无法返回跳点的网络仍作为一条端到端逻辑路径正常管理。

路径 MTU 可通过逐步改变探测包大小并设置禁止 IP 分片进行测量。MPUDP 切片大小应取该路径已验证 MTU，扣除 IP、UDP、MPUDP、认证标签和隧道包头后的安全值。

## 6.5 真实业务流被动测量

主动探测反映轻量测试包的状态，不能完全替代视频业务负载下的实际表现。视频传输期间，聚合服务器根据 MPUDP 包头和接收时间持续生成以下指标：

- 按 `path_id` 统计接收字节数和实际交付速率。
- 根据 `packet_seq` 统计序号缺口、网络重复包和乱序深度。
- 根据发送与接收时间计算时延和抖动。
- 根据 `deadline` 统计到达但已经失去播放价值的过期包。
- 统计 CRC 差错、GCM 认证失败、FEC 恢复和 NACK 重传结果。
- 通过 ACK 返回接收区间和接收时间，供路由器计算 RTT、在途数据及拥塞窗口。

这种方式只解析本系统自定义包头和传输元数据，不需要读取视频明文，也不需要混杂模式嗅探其他设备的数据包。它是链路调度、拥塞控制和 QoE 评价的主要数据来源。

## 6.6 拓扑数据结构

拓扑在内存中使用“属性图 + 时序样本”的组合结构。图描述节点、链路和连接关系，时序数据描述每条链路随时间变化的质量。

### 6.6.1 节点

`Node` 表示聚合路由器、网络接口、可选中间跳点和聚合服务器入口：

```json
{
  "node_id": "router-01:wwan0",
  "node_type": "interface",
  "device_id": "router-01",
  "name": "wwan0",
  "addresses": ["10.20.0.2/24"],
  "attributes": {
    "link_type": "5G",
    "mtu": 1420,
    "operator": "operator-a"
  },
  "last_seen": "timestamp"
}
```

### 6.6.2 链路与路径

`Link` 表示两个节点之间的逻辑连接，`Path` 表示从聚合路由器某个出口到服务器入口的端到端路径：

```json
{
  "path_id": "path_5g_01",
  "session_id": "session-uuid",
  "source_node": "router-01:wwan0",
  "destination_node": "server-01:mpudp-9000",
  "link_type": "5G",
  "source_address": "10.20.0.2:41001",
  "observed_address": "203.0.113.10:52001",
  "gateway": "10.20.0.1",
  "route_table": 101,
  "status": "available",
  "path_mtu": 1420,
  "hop_list": [],
  "version": 3
}
```

内存图使用邻接表保存连接关系，并使用哈希表按 `node_id`、`path_id` 和 `session_id` 快速查找。调度器只读取当前有效的路径版本，不直接扫描历史测量数据。

### 6.6.3 链路质量样本

链路质量采用追加写入的时序记录：

```json
{
  "time": "timestamp",
  "session_id": "session-uuid",
  "path_id": "path_5g_01",
  "rtt_ms": 42.5,
  "jitter_ms": 6.1,
  "loss_rate": 0.012,
  "reorder_rate": 0.004,
  "delivery_rate_bps": 8200000,
  "queue_delay_ms": 8.4,
  "crc_error_rate": 0.0,
  "auth_failure_rate": 0.0,
  "expired_rate": 0.003,
  "qoe_score": 0.91
}
```

链路当前状态由最近一个滑动窗口的样本聚合得到；原始样本用于回放实验、分析链路变化和验证调度算法。

## 6.7 数据保存位置

数据按“路由器短期缓存、服务器集中持久化”保存：

| 位置 | 存储内容 | 固定实现 |
|---|---|---|
| 聚合路由器内存 | 当前接口、路由、路径状态、拥塞窗口和调度权重 | 邻接表和哈希表 |
| 聚合路由器本地磁盘 | 静态链路配置、最后一次有效拓扑、断网期间待上报事件 | SQLite |
| 聚合服务器内存 | 全部在线路由器的当前拓扑和最近滑动窗口 | 图结构、哈希表和环形缓冲区 |
| 聚合服务器数据库 | 节点、路径版本、状态变化和安全事件 | PostgreSQL |
| 聚合服务器时序库 | RTT、丢包、抖动、吞吐量、拥塞和 QoE 样本 | PostgreSQL + TimescaleDB |

路由器不长期保存视频包和全量抓包文件。断网时只在 SQLite 中缓存必要的拓扑变化和聚合指标，恢复连接后批量上报。服务器按照保存周期对高频样本进行降采样，例如短期保留原始样本，长期只保留分钟级或小时级聚合结果。

建议的核心关系表如下：

```text
topology_nodes(
    node_id, node_type, device_id, attributes, first_seen, last_seen
)

topology_paths(
    path_id, version, source_node, destination_node, link_type,
    gateway, route_table, observed_address, path_mtu, status,
    valid_from, valid_to
)

link_samples(
    time, session_id, path_id, rtt_ms, jitter_ms, loss_rate,
    reorder_rate, delivery_rate_bps, queue_delay_ms,
    crc_error_rate, auth_failure_rate, expired_rate, qoe_score
)

topology_events(
    time, device_id, path_id, event_type, old_value, new_value, reason
)
```

## 6.8 拓扑更新与版本管理

以下事件会触发拓扑更新：

- 网卡新增、移除、启用或关闭。
- IP 地址、默认网关、策略路由或 MTU 改变。
- 聚合服务器观察到的 NAT 地址发生变化。
- 探测连续失败导致路径从可用变为不可用。
- 中间跳点或路径 MTU 发生变化。
- 断开后重新建立新的 MPUDP/QUIC 会话。

拓扑变化时不覆盖原记录，而是关闭旧路径版本的 `valid_to`，再写入新版本。这样可以根据实验时间还原当时使用的接口、地址、路径和链路质量，解释某次调度、丢包或 QoE 下降的原因。

## 6.9 拓扑获取与使用流程

```text
聚合路由器启动
      │
      ▼
Netlink 读取接口、地址、网关、MTU 和策略路由
      │
      ▼
为光纤 / 5G / Wi-Fi 出口分别生成稳定 path_id
      │
      ▼
绑定源接口发送认证 UDP 探测包
      │
      ▼
聚合服务器返回可达性、时间戳和观察到的 NAT 地址
      │
      ▼
建立“路由器接口 → 逻辑异构链路 → 服务器入口”属性图
      │
      ▼
MPUDP 真实业务流 + QUIC ACK 持续更新链路时序指标
      │
      ├── 当前状态进入内存图，供 Link Monitor 和 Scheduler 使用
      ├── 路由器断网缓存进入本地 SQLite
      └── 拓扑版本与历史指标写入服务器 PostgreSQL/TimescaleDB
      │
      ▼
多路径调度、拥塞控制、故障切换和 QoE 分析
```

## 6.10 安全与性能约束

- 所有主动探测包必须认证并具备序号、时间戳和 nonce，服务器拒绝伪造、过期和重放探测包。
- 探测服务必须限速，防止被利用进行流量放大或消耗服务器资源。
- 拓扑数据库包含设备地址、运营商和网络路径等敏感信息，需要访问控制、传输加密和日志审计。
- 不保存无关设备流量，不长期保存视频明文或完整抓包，实验抓包应设置容量和保留时间上限。
- 拓扑采集不能阻塞 MPUDP 视频发送；高频指标应在内存中聚合后批量写入数据库。
- 系统时间需要通过 NTP/PTP 等方式同步。时钟无法可靠同步时，以 RTT 和相对时间为主，不直接使用单向时延作调度依据。

通过上述方式，系统获得的是一张能够持续更新、可存储、可回放并可直接服务于调度算法的逻辑网络拓扑，而不是一张依赖人工绘制或全量嗅探得到的静态图片。
