# 第 4 章 传输协议基础

## 4.1 RTP/RTCP

RTP 是实时音视频传输协议，常与 UDP 配合使用。RTP 包头中的 sequence number、timestamp、payload type 和 SSRC 对视频流排序、同步和统计具有参考价值。

RTCP 可用于接收质量反馈，包括丢包、抖动和往返时延等信息。自定义聚合协议可以参考 RTP/RTCP 的设计思想。

## 4.2 GB/T 28181
GB/T 28181《公共安全视频监控联网系统信息传输、交换、控制技术要求》是我国公共安全视频监控系统中非常重要的联网标准，现行版本为 GB/T 28181-2022。该标准主要规定不同厂商、不同层级的视频监控设备和平台之间如何完成设备注册、目录查询、实时视频点播、录像回放、云台控制、报警通知以及平台级联等操作，从而实现跨设备、跨平台的视频监控系统互联互通。

在本项目中，GB/T 28181 可以作为前端监控设备接入聚合路由器的标准协议。监控摄像头首先通过 SIP 向聚合路由器或接入平台完成注册和状态维护；当系统需要获取某一路视频时，通过 SIP/SDP 建立媒体会话，随后摄像头通过 RTP/RTCP 将 H.264/H.265 视频流发送至聚合路由器。聚合路由器接收到视频后，再进行解析、加密、分片和多链路调度，并通过后续异构网络传输至聚合服务器。


## 4.3 GB/35114
GB 35114-2017《公共安全视频监控联网信息安全技术要求》是面向公共安全视频监控联网系统的信息安全标准，目前仍为现行国家标准。该标准主要针对视频监控系统联网过程中可能存在的身份冒用、非法设备接入、视频数据泄露以及信息被篡改等安全问题，对设备身份认证、系统接入认证、数据完整性保护和视频信息安全传输等方面提出要求。

在本项目中，GB 35114 可以作为“视频安全传输模块”的标准参考。对于监控摄像头采集的视频，在进入聚合路由器以及通过异构网络向聚合服务器传输时，可以参考该标准设计身份认证、视频数据加密、完整性校验和安全接入机制，从而保证视频数据在光纤、5G、Wi-Fi 等不同链路上传输过程中的机密性、完整性和可信性。


## 4.4 GA/T 1400.4 
GA/T 1400.4-2017《公安视频图像信息应用系统 第4部分：接口协议要求》是面向公安视频图像信息应用系统的数据交换接口规范，目前属于现行的公安行业推荐性标准。该标准主要规定视频图像信息系统之间的接口类型、资源描述、消息交互和接口安全等内容，其接口主要包括采集接口、数据服务接口、级联接口和分析接口，并采用 REST 架构，通过 URI 对资源进行标识，支持基于 HTTP 的信息交换。

在本项目中，GA/T 1400.4 可以主要应用在聚合服务器和 AI Agent 后端。当聚合服务器恢复视频并由 AI Agent 完成人员、车辆、异常事件等视频内容分析后，可以按照 GA/T 1400.4 的接口形式，将分析得到的结构化信息、图片、视频片段、标签和告警信息上传到上层视频图像应用平台或数据库，也可以接受上层平台下发的分析任务。

## 4.6 MPTCP 基础

MPTCP 是 TCP 的多路径扩展，可通过多个子流同时传输数据。其优点是对应用透明、可靠性较好，但仍然继承 TCP 的有序交付和队头阻塞问题。

对于实时视频回传，MPTCP 可作为多链路传输的对比技术，但不一定是最低时延场景下的最优选择。

## 4.7 MPUDP 基础

MPUDP 通常不是单一标准协议，而是指基于 UDP 构建的多路径传输机制。其典型做法是在 UDP 之上自定义聚合协议头，并由聚合路由器根据链路状态将视频数据分发到多条链路。

MPUDP 的优势是灵活、低时延、可控制性强，适合实现链路质量感知、包级调度、乱序重排、FEC、NACK、关键帧冗余和实时丢弃策略。

其主要不足是可靠性、拥塞控制、乱序处理和安全机制需要自行设计，工程复杂度高于直接使用成熟协议。

## 4.8 SCTP 基础

SCTP 是一种独立传输层协议，支持多流、多宿主、可靠传输和消息边界保持。与 TCP 相比，SCTP 的多流能力可以降低部分队头阻塞影响，多宿主能力可以用于链路故障切换。

但 SCTP 在公网环境中的部署普及度不如 TCP/UDP，NAT 和防火墙穿透也更复杂。在本课题中，SCTP 更适合作为控制信令、链路状态上报和设备管理通道，而不是视频数据主通道。

## 4.9 MPTCP、MPUDP、SCTP 用法对比

| 协议 | 核心定位 | 优点 | 局限 | 推荐用途 |
|---|---|---|---|---|
| MPTCP | 可靠多路径 TCP | 对应用透明、内核支持、可靠传输、链路容灾 | 队头阻塞、重传等待、调度不易自定义 | 对比方案、文件/日志回传、非强实时数据 |
| MPUDP | 自定义低时延多路径 UDP | 灵活、低时延、适合包级调度和视频感知传输 | 需要自行处理可靠性、拥塞和乱序 | 视频数据主通道、核心实验方案 |
| SCTP | 多流多宿主可靠传输 | 消息边界、多流、多宿主、适合信令 | 公网部署受限、视频生态较弱 | 控制信令、状态上报、设备管理 |

面向无人机、无人车实时图像回传，推荐采用如下分工：

```text
主要测试 数据面：MPUDP
控制面：TCP / QUIC / SCTP
对比方案：MPTCP
```

## 4.10 聚合服务器端差错检测与恢复机制

视频切片经过光纤、5G、Wi-Fi、卫星或公网等异构链路传输时，可能出现丢包、比特差错、数据篡改、乱序到达和重复到达等问题。聚合服务器需要在解密和视频恢复之前，对多条链路接收到的数据包进行统一校验、去重、重排和丢包恢复，避免错误数据继续进入视频解码和 AI 分析模块。

### 4.10.1 视频切片包头设计

聚合路由器对视频数据分片时，应为每个切片增加自定义传输包头。包头可包含以下字段：

| 字段 | 作用 |
|---|---|
| 协议版本和包头长度 | 支持协议识别及后续扩展 |
| 视频流标识（Stream ID） | 区分不同摄像头或视频会话 |
| 帧编号（Frame ID） | 标识切片所属的视频帧 |
| 切片编号和切片总数 | 判断一帧是否完整并完成切片重组 |
| 全局序列号（Sequence Number） | 检测丢包、乱序和重复包 |
| 发送时间戳 | 计算端到端时延、抖动和超时 |
| 链路标识（Path ID） | 区分光纤、5G、Wi-Fi 等传输路径 |
| 数据类型和关键帧标志 | 区分 I 帧、P 帧、控制包及 FEC 包 |
| 载荷长度 | 检查报文长度是否合法 |
| 校验和（CRC32） | 检测传输中的随机比特差错 |
| 认证标签（AEAD Tag 或 HMAC） | 检测数据篡改并验证数据完整性和来源 |

CRC32 只能用于检测链路噪声等原因造成的随机差错，不能抵抗攻击者重新计算校验和后的恶意篡改。需要安全保护时，可采用 AES-GCM 或 ChaCha20-Poly1305 等认证加密算法，使视频载荷和关键包头字段同时受到完整性保护。

### 4.10.2 服务器端差错检测

聚合服务器收到数据包后，首先检查协议版本、包头长度、载荷长度和 Stream ID 等基本字段。随后验证认证标签和 CRC32：认证失败说明数据可能被篡改、密钥不一致或包头损坏；CRC32 错误说明传输过程中可能出现比特差错。校验失败的数据包应直接丢弃并记录其来源链路，不能进入后续视频重组过程。

服务器以 Stream ID、Frame ID、切片编号和全局序列号建立接收窗口。若相同序列号或相同切片已经到达，则将后到的数据包判定为重复包并丢弃；若序列号未按顺序到达，则先将数据包放入重排缓冲区。当某个序列号在设定时间内仍未到达，或帧的切片数量不完整时，将其判定为丢包。服务器还应分别统计各条链路的丢包率、差错率、重复率、乱序深度、时延和抖动，为后续多路径调度和 QoE 分析提供反馈。

### 4.10.3 差错恢复方法

不同恢复方法会产生不同的时延开销，因此应根据视频帧类型和播放截止时间进行选择：

1. **乱序重排：** 在较短的重排等待窗口内缓存提前到达的切片，并按照全局序列号和切片编号恢复正确顺序。超过等待时间的数据包按丢包处理，避免缓冲时间过长。
2. **重复包消除：** 根据全局序列号或“Stream ID + Frame ID + 切片编号”进行判重，只保留第一份通过完整性校验的数据包。
3. **FEC 前向纠错：** 当缺失切片数量不超过冗余恢复能力时，优先使用 FEC 包恢复原始数据，无须等待发送端重传，适合高时延或抖动较大的链路。
4. **选择性重传：** FEC 无法恢复且距离播放截止时间仍然充足时，通过 NACK 只请求缺失或损坏的切片。发送端收到请求后，可选择当前质量更好的链路进行重传。
5. **关键帧请求：** 如果丢失的是关键帧、连续多个参考帧不可恢复，或解码器已经无法继续正确解码，可通过 RTCP PLI/FIR 等反馈机制请求新的关键帧，使视频尽快恢复正常。频繁请求关键帧会明显增加码率，因此不宜作为普通丢包的首选方案。
6. **超时丢弃和错误隐藏：** 当切片已经超过播放截止时间，继续重传将失去意义。服务器应丢弃过期数据，并由解码器采用帧复制、运动补偿等错误隐藏方法减小画面跳变。
7. **链路反馈与重新调度：** 当某条链路持续出现高丢包、高差错或高时延时，服务器向聚合路由器反馈链路质量，降低该链路的调度权重，并可对关键帧或重要切片采用跨链路冗余发送。

总体处理优先级可设计为“FEC 恢复优先、可按时完成时选择性重传、无法继续解码时请求关键帧、超过截止时间后及时丢弃”。这样可以在视频完整性、实时性和带宽开销之间取得平衡。

### 4.10.4 技术路线

```text
异构链路多路径数据包
          │
          ▼
聚合服务器多链路接收
          │
          ▼
包头合法性检查 → CRC32 差错检测 → AEAD/HMAC 篡改检测
          │
          ▼
重复包检测与消除 → 乱序缓存与重排 → 丢包及超时判断
          │
          ▼
FEC 恢复 → NACK 选择性重传 → 必要时请求新的关键帧
          │
          ▼
视频切片重组 → 解密/解码 → QoE 统计 → AI Agent
          │
          └── 链路质量反馈 → 聚合路由器多路径调度
```
