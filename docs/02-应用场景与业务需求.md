# 第 2 章 应用场景与业务需求

本章面向无人机、无人车实时图像回传场景，分析视频流在进入聚合路由器之前和进入聚合路由器之后需要完成的处理工作，并说明其对 MPUDP、MPTCP 等多路径传输技术的需求。

在本实验模型中，视频流并不是直接从摄像头原始画面进入网络传输，而是需要经过采集、编码、封装、接入、标识、缓存、分包和调度等环节，最后才由聚合路由器通过异构链路发送到聚合服务器。

整体处理链路如下：

```text
无人机 / 无人车摄像头
        ↓
视频采集与编码
        ↓
视频封装与推流
        ↓
聚合路由器视频流接入
        ↓
流标识、解析、分包、封装
        ↓
MPUDP / MPTCP 多路径传输
        ↓
聚合服务器接收、重组、恢复输出
```

## 2.1 无人机实时图像回传特点

无人机场景下，实时图像回传通常具有高移动性、空地链路波动明显、视距与非视距状态频繁变化等特点。无人机在飞行过程中，其高度、姿态、距离、遮挡环境和无线信号质量会持续变化，导致视频回传链路的带宽、时延、抖动和丢包率不断波动。

主要特点包括：

- 高移动性：无人机飞行速度快，位置变化明显，链路质量具有动态性。
- 空地链路波动明显：飞行高度、天线方向、遮挡物和电磁环境都会影响通信质量。
- 视距和非视距切换频繁：从开阔区域进入建筑、山体、树木遮挡区域后，链路质量可能急剧下降。
- 对实时性要求高：巡检、安防、应急、侦察等任务需要较低图像延迟。
- 可能存在链路遮挡和突发中断：单链路传输容易造成画面冻结、卡顿或长时间丢失。

对聚合传输系统而言，无人机场景更强调链路快速感知、故障切换、低时延调度和关键视频数据保护。

## 2.2 无人车实时图像回传特点

无人车场景下，实时图像回传主要受到地面环境、道路结构、建筑遮挡、无线覆盖和多摄像头并发的影响。无人车通常可以搭载更多通信设备和计算设备，因此更适合部署多 5G 模组、Wi-Fi、专网电台、以太网调试口和边缘计算单元。

主要特点包括：

- 地面障碍物多：建筑、车辆、墙体、隧道、地下空间等会造成信号遮挡。
- 城市道路环境复杂：无线信道容易受到多径、干扰和基站切换影响。
- 4G/5G、Wi-Fi、专网混合接入：车载平台通常具备多种网络接入条件。
- 视频流连续性要求高：远程巡检、远程驾驶和现场监控需要尽量避免画面中断。
- 可能同时传输多路摄像头画面：前视、后视、环视、云台相机等会形成多路并发视频流。

对聚合传输系统而言，无人车场景更强调多路视频流管理、稳定带宽利用、链路切换连续性和多链路协同调度。

## 2.3 视频流业务需求

无人机、无人车实时图像回传不是普通文件传输，而是对时延、抖动、连续性和画面可用性高度敏感的实时媒体业务。

核心需求包括：

- 低时延：从图像采集、编码、聚合路由器转发到服务器恢复输出的整体延迟应尽量降低。
- 低抖动：相邻视频包到达间隔应尽量稳定，避免服务器端重组缓存和播放端缓存压力过大。
- 可接受范围内的丢包恢复：实时视频可以容忍少量普通帧丢失，但关键帧和连续丢包需要重点保护。
- 链路切换不中断：单条链路劣化或断开时，视频数据应快速迁移到其他可用链路。
- 图像质量稳定：在带宽波动时，应尽量减少花屏、马赛克、卡顿、黑屏和长时间冻结。
- 多路视频并发支持：系统应支持同一无人车或多架无人机同时上传多路视频流。
- 安全传输：现场图像可能涉及敏感信息，需要具备身份认证、加密和完整性校验能力。

这些需求决定了聚合路由器不能只做简单转发，而需要理解视频流边界、维护流标识，并根据链路状态选择合适的传输策略。

## 2.4 关键性能指标

关键性能指标用于评价聚合路由器到聚合服务器之间的视频回传质量。

| 指标 | 含义 | 关注原因 |
|---|---|---|
| 端到端传输时延 | 从视频产生到服务器恢复输出之间的总时延 | 影响远程观察和控制实时性 |
| 聚合段传输时延 | 从聚合路由器发出到聚合服务器接收重组之间的时延 | 直接评价聚合传输过程 |
| 抖动 | 数据包到达间隔的波动程度 | 影响重排缓存和播放稳定性 |
| 丢包率 | 发送包与接收包之间的缺失比例 | 影响画面完整性和恢复策略 |
| 乱序率 | 数据包未按原始顺序到达的比例 | 反映多路径传输带来的重排压力 |
| 有效吞吐量 | 实际可用于视频数据的吞吐能力 | 影响可承载的视频码率 |
| 视频卡顿次数 | 播放或恢复过程中出现停顿的次数 | 直接反映用户观看体验 |
| 视频帧恢复率 | 成功恢复并输出的视频帧比例 | 反映重组和丢包恢复能力 |
| 链路切换时间 | 链路异常后切换到其他链路所需时间 | 影响故障场景下的视频连续性 |
| 故障恢复时间 | 链路恢复后重新加入聚合传输所需时间 | 影响多链路资源利用效率 |

在实验中，应同时记录网络层指标和视频层指标。网络层指标说明链路传输效果，视频层指标说明最终画面是否可用。

## 2.5 视频流接入与转发技术

视频流接入与转发技术用于把无人机、无人车的视频流接入聚合路由器，并在聚合服务器端恢复输出。该部分连接视频业务和网络传输，是后续 MPUDP、MPTCP 多路径传输的前置环节。

需要掌握的技术包括：

- FFmpeg：用于拉流、推流、转封装、录制、码流分析和实验数据生成。
- GStreamer：用于构建实时视频处理 pipeline，适合嵌入式和边缘设备场景。
- RTP / RTSP：常见实时视频传输与控制协议，适合摄像头、编码器和视频平台接入。
- UDP 推流：低时延、低开销，适合 MPEG-TS/UDP、RTP/UDP 等实时视频输入。
- SRT 推流：适合不稳定网络下的可靠视频传输，可作为实验对比或外部接入方式。
- WebRTC 基础：适合浏览器端低时延观看和交互式视频分发。
- H.264 / H.265 裸流：视频编码后的基本码流形式，是识别 NALU、帧类型和关键帧的基础。
- MPEG-TS 封装：适合实时传输和 UDP 推流，容错性较好。
- FLV / MP4 / TS 容器基础：用于理解视频数据封装、时间戳、音视频轨道和文件保存。
- 多路视频流标识与管理：用于区分不同无人平台、不同摄像头和不同任务视频流。

本课题中的视频流接入不建议一开始就做复杂解码和图像处理。更合理的方式是尽量保持编码后码流不变，只在聚合路由器侧完成必要的解析、分包、标识和传输封装。

## 2.6 视频流进入聚合路由器前的处理

视频流进入聚合路由器之前，通常已经完成图像采集和视频编码。无人机、无人车上的摄像头输出原始图像后，由编码器或边缘计算模块压缩为 H.264/H.265 码流，再通过某种封装格式推送到聚合路由器。

### 2.6.1 图像采集

图像采集由无人机、无人车上的摄像头完成。常见视频源包括云台相机、前视相机、环视相机、红外相机、深度相机和全景相机。

对于聚合传输实验，重点不是摄像头成像过程，而是摄像头输出的视频流参数，包括：

- 分辨率：如 720p、1080p、2K、4K。
- 帧率：如 25 fps、30 fps、60 fps。
- 码率：如 1 Mbps、2 Mbps、4 Mbps、8 Mbps。
- 编码格式：H.264 或 H.265。
- 关键帧间隔：影响关键帧丢失后的恢复速度。
- 视频路数：单路摄像头或多路摄像头并发。

这些参数决定了聚合路由器后续需要承载的数据规模和实时性压力。

### 2.6.2 视频编码

原始图像数据量非常大，不适合直接通过移动链路回传，因此需要先进行视频编码。常见编码方式包括 H.264 和 H.265。

编码后视频流通常由以下帧类型组成：

- I 帧：关键帧，可独立解码，丢失后影响较大。
- P 帧：依赖前向参考帧，丢失后会影响局部连续画面。
- B 帧：依赖前后参考帧，压缩效率高，但会增加编码和传输延迟。

实时回传场景通常倾向于低延迟编码配置，例如缩短编码缓存、减少或不用 B 帧、控制 GOP 长度、限制码率峰值。这些设置能降低传输压力，也能减少丢包后的画面恢复时间。

### 2.6.3 视频封装

编码后的 H.264/H.265 裸流一般需要封装后再传输。常见封装和输入形式包括：

- RTP/UDP：适合实时视频，带有 RTP 序号和时间戳。
- RTSP：通常作为摄像头或编码器的控制与拉流协议，媒体数据多通过 RTP 承载。
- MPEG-TS/UDP：适合实时推流和工程测试，容易与 FFmpeg/GStreamer 对接。
- SRT：适合不稳定网络环境下的视频推流，带有重传和延迟缓冲机制。
- RTMP/FLV：适合直播平台接入，但时延通常高于纯 RTP/UDP 方案。
- MP4：更适合文件保存和点播，不适合作为低时延实时传输主格式。

在进入聚合路由器之前，推荐采用 RTP/UDP 或 MPEG-TS/UDP 作为实验输入格式，因为它们便于低时延接入和包级处理。

## 2.7 聚合路由器内的视频流处理流程

视频流进入聚合路由器后，需要先完成接入适配，再进入多路径传输模块。聚合路由器的处理目标是把上游视频流转换为适合异构链路传输的聚合数据包。

### 2.7.1 接入适配

接入适配负责接收不同来源和不同格式的视频流。

典型方式包括：

- 使用 FFmpeg 从 RTSP 摄像头拉流，再转为 RTP/UDP 或 MPEG-TS/UDP 输入聚合模块。
- 使用 GStreamer 从摄像头、编码器或 UDP 端口接收视频流，再通过 appsrc/appsink 与聚合程序对接。
- 直接监听 RTP/UDP 或 MPEG-TS/UDP 端口，接收上游已经封装好的实时视频包。
- 接收 SRT 输入流，将其解封装后交给聚合传输模块。

接入适配阶段应尽量避免完整解码视频画面，除非实验需要做图像识别、码率重编码或帧级内容分析。对于传输实验，更推荐保持编码码流不变，以降低聚合路由器 CPU 占用和处理时延。

### 2.7.2 解封装与码流解析

聚合路由器需要根据输入格式决定是否解封装：

- 对 RTP 输入：可保留 RTP 包，也可提取 RTP payload 后重新封装到聚合协议中。
- 对 MPEG-TS 输入：可按 TS 包或 PES 边界组织数据，再封装到聚合数据包中。
- 对 H.264/H.265 裸流输入：需要识别 NALU 边界，避免随意切断关键结构。
- 对 SRT 输入：通常先由 SRT 层恢复为连续媒体流，再进入聚合模块。

码流解析不一定要完整理解视频内容，但建议至少识别以下信息：

- 视频流编号。
- 包或帧的时间戳。
- H.264/H.265 NALU 边界。
- 关键帧或普通帧标识。
- 单个帧对应的数据范围。
- 上游包序号或 RTP 序号。

这些信息可用于后续流管理、关键帧保护、分包和服务器端重组。

### 2.7.3 多路视频流标识

无人机和无人车可能同时回传多路视频，因此聚合路由器需要为每一路视频建立唯一标识。

建议使用以下标识字段：

- device_id：无人机或无人车编号。
- camera_id：摄像头编号，如前视、后视、云台、红外等。
- flow_id：聚合传输内部的视频流编号。
- session_id：一次任务或一次连接的会话编号。
- codec：视频编码格式，如 H.264 或 H.265。
- input_type：输入格式，如 RTP、MPEG-TS、RTSP、SRT。

服务器端需要使用这些字段区分不同视频流，避免多个无人平台或多个摄像头的数据混在一起。

### 2.7.4 分包与 MTU 控制

视频帧可能大于单个网络包可承载的数据量，因此聚合路由器需要进行分包。分包时必须考虑路径 MTU，尤其是在 VPN、WireGuard、GRE、VXLAN、IPSec 等隧道存在时，额外封装头会减少可用负载空间。

分包原则包括：

- 单个聚合数据包应尽量小于路径 MTU，避免 IP 层分片。
- 不应随意切断 H.264/H.265 的关键结构，必要时按 NALU 或 RTP payload 边界切分。
- 每个分包都应包含全局序号、流标识、时间戳和片段信息。
- 同一视频帧的多个分包应能在服务器端重新归组。
- 对 I 帧数据可设置更高优先级或冗余保护标识。

建议聚合包头至少包含：

```text
flow_id        视频流编号
seq            全局包序号
timestamp      发送时间戳或视频时间戳
frame_id       视频帧编号
frag_index     当前帧内分片序号
frag_count     当前帧分片总数
frame_type     I/P/B 帧或未知
payload_len    负载长度
flags          FEC、重传、冗余、关键帧等标志
checksum       校验字段
```

### 2.7.5 缓存与队列管理

聚合路由器在发送前需要维护缓存和队列。缓存用于吸收上游视频输入抖动，队列用于等待链路调度和发送。

常见队列包括：

- input queue：接收上游视频包。
- packetization queue：等待解析和分包。
- priority queue：根据帧类型、deadline 或流优先级排序。
- per-path queue：每条链路独立发送队列。
- retransmission buffer：短时间保存已发送包，用于 NACK 重传。

实时视频队列不能无限增长。队列过长会造成时延积累，因此需要设置队列上限和过期丢弃策略。例如，当普通 P/B 帧超过传输 deadline 时，可优先丢弃；I 帧或关键数据则尽量保护。

## 2.8 基于 MPUDP 的视频流传输处理

MPUDP 适合作为本实验模型的视频数据主通道。它基于 UDP 构建多路径传输机制，由聚合路由器自主完成包级调度、链路选择、冗余控制和发送速率控制。

### 2.8.1 MPUDP 发送流程

基于 MPUDP 的视频发送流程如下：

```text
视频输入
  ↓
解封装 / 码流解析
  ↓
添加 flow_id、seq、timestamp、frame_type
  ↓
按 MTU 分包
  ↓
链路质量评估
  ↓
包级调度
  ↓
不同 UDP socket 绑定不同链路发送
```

聚合路由器可以为每条链路维护独立 UDP socket，并通过源 IP 绑定、策略路由或 `SO_BINDTODEVICE` 控制数据包从指定接口发出。

### 2.8.2 MPUDP 调度策略

MPUDP 可以支持多种调度方式：

- 单链路模式：只使用当前质量最好的链路。
- 主备模式：主链路异常时切换到备用链路。
- 轮询模式：按顺序将视频包分配到不同链路。
- 加权调度：按链路带宽、时延、丢包和抖动设置发送比例。
- 视频感知调度：I 帧或关键数据走高质量链路，普通帧按比例分发。
- 冗余调度：关键帧、头信息或控制数据复制到多条链路。

由于 MPUDP 不依赖传输层有序交付，服务器端必须处理乱序、重复和丢包。其优势是低时延和灵活性，适合无人机、无人车实时视频回传实验。

### 2.8.3 MPUDP 服务器恢复

聚合服务器接收 MPUDP 数据后，需要执行：

- 解析聚合包头。
- 按 flow_id 区分视频流。
- 根据 seq 去重和排序。
- 根据 frame_id、frag_index、frag_count 重组视频帧。
- 根据 timestamp 判断过期包。
- 根据 gap detection 发现丢包。
- 根据 FEC 或 NACK 机制尝试恢复。
- 恢复为 RTP/UDP、MPEG-TS、WebRTC、RTMP 或文件输出。

MPUDP 的重点是让服务器端掌握足够的包级信息，从而在多链路乱序条件下恢复连续可用的视频流。

## 2.9 基于 MPTCP 的视频流传输处理

MPTCP 适合作为本实验模型的对比方案或可靠传输方案。它在内核层将一个 TCP 连接拆分为多个子流，通过多条链路传输。应用层看到的仍然是普通 TCP 连接。

### 2.9.1 MPTCP 传输方式

基于 MPTCP 的视频传输可以采用以下方式：

- 将视频流封装为基于 TCP 的协议，如 RTSP over TCP、RTMP/FLV 或自定义 TCP 流。
- 在支持 MPTCP 的 Linux 内核上开启 MPTCP。
- 聚合路由器和聚合服务器之间建立一个 MPTCP 连接。
- 内核根据可用链路建立多个 TCP subflow。
- 应用层按普通 TCP socket 读写视频数据。

其逻辑如下：

```text
视频封装流
  ↓
普通 TCP socket
  ↓
MPTCP 内核协议栈
  ├── 5G subflow
  ├── Wi-Fi subflow
  └── 专网 subflow
  ↓
聚合服务器 TCP 接收流
```

### 2.9.2 MPTCP 对视频流处理的影响

MPTCP 的优势是可靠、有序、对应用透明，不需要聚合路由器显式处理每个包走哪条链路。但它也会带来实时视频场景中的典型问题：

- TCP 有序交付可能造成队头阻塞。
- 丢包后等待重传会增加时延。
- 不同链路 RTT 差异过大时，慢路径可能拖累整体输出。
- 应用层较难直接控制某个视频帧走哪条链路。
- 不适合灵活实现关键帧冗余、帧级 deadline 和实时丢弃策略。

因此，MPTCP 更适合作为可靠基线方案，用于和 MPUDP 比较吞吐、时延、卡顿、丢包恢复和链路故障切换效果。

### 2.9.3 MPUDP 与 MPTCP 的分工

在本课题中，两者可按以下方式定位：

| 传输方式 | 适用角色 | 视频流处理特点 |
|---|---|---|
| MPUDP | 视频数据主实验方案 | 聚合路由器显式分包、标识、调度，服务器显式去重、重排、恢复 |
| MPTCP | 对比实验方案或可靠传输方案 | 应用层按连续字节流处理，内核负责多路径，可靠但可能增加时延 |

对于实时图像回传，建议优先研究 MPUDP，因为它更便于体现异构链路下的视频业务感知传输。MPTCP 则用于说明传统可靠多路径传输在实时视频中的优势和局限。

## 2.10 聚合服务器端恢复输出

视频流经过 MPUDP 或 MPTCP 到达聚合服务器后，需要恢复为后续系统可使用的视频形式。

### 2.10.1 MPUDP 恢复输出

MPUDP 场景下，服务器需要先完成包级恢复，再输出媒体流：

```text
多链路 UDP 接收
  ↓
解析聚合包头
  ↓
按 flow_id 分类
  ↓
去重、排序、丢包检测
  ↓
按 frame_id 和分片信息重组
  ↓
恢复 RTP / MPEG-TS / H.264/H.265 码流
  ↓
输出到播放器、流媒体服务器或文件
```

输出方式可包括 UDP/RTP、MPEG-TS/UDP、SRT、RTMP、WebRTC 或文件存储。实验阶段可优先输出为 MPEG-TS/UDP 或文件，便于验证和分析。

### 2.10.2 MPTCP 恢复输出

MPTCP 场景下，服务器侧应用层收到的是可靠有序字节流，因此不需要像 MPUDP 那样显式处理包级乱序。但仍需要完成视频协议层的解析和输出。

典型处理包括：

- 从 TCP 字节流中解析 RTSP、RTMP/FLV、自定义帧边界或 MPEG-TS 数据。
- 恢复媒体时间戳。
- 检查码流连续性。
- 输出到播放器、流媒体服务器或文件。

MPTCP 的服务器恢复逻辑较简单，但时延可控性较弱。因此在评价时应重点观察其是否因为重传等待和队头阻塞导致视频卡顿。

## 2.11 本章小结

无人机、无人车实时图像回传对低时延、低抖动、连续性、链路切换、图像质量和多路并发提出了较高要求。视频流在经由聚合路由器传输前，需要完成编码、封装、接入适配、码流解析、流标识、MTU 分包、缓存队列和传输封装等处理。

从技术路线看，MPUDP 更适合作为实时视频聚合回传的核心实验方案，因为它可以灵活实现包级调度、链路质量感知、关键帧保护、乱序重排和实时丢弃。MPTCP 更适合作为可靠多路径对比方案，用于分析可靠有序传输在异构链路视频回传中的优势和局限。

本章为后续异构聚合网络架构、传输协议设计、Linux 多网卡路由、网络质量测量和实验评估提供业务需求与视频流处理基础。
